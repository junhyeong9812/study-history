## 1. 출발점: 왜 계층 모델인가

### 1.1 네트워크의 근본 문제

```
컴퓨터 A가 컴퓨터 B에게 데이터를 보내려면:
  물리적 연결 (전선, 무선), 주소 지정 (누구에게?),
  경로 설정 (어떤 길로?), 오류 검출/복구, 흐름/혼잡 제어...

이 모든 것을 하나의 프로토콜로 처리하면?
  → 복잡도가 폭발. 하나를 바꾸면 전체가 영향받음.

해결: 계층화 (Layering)
  각 계층이 하나의 관심사만 처리.
  아래 계층이 위 계층에게 서비스를 제공.
  각 계층은 독립적으로 변경 가능.
  
  우편 비유:
    편지를 쓴다 (내용) → 봉투에 넣고 주소를 쓴다 (주소 지정) → 
    우체통에 넣는다 (전달) → 우체국이 분류한다 (경로) →
    배달부가 가져다준다 (물리적 전달)
    
    각 단계가 독립적! 편지 내용을 바꿔도 배달 방식은 그대로.
```

### 1.2 OSI 7계층 vs TCP/IP 4계층

```
🔴 [외워야 할 체계]

OSI 7계층 (이론적 참조 모델):

  계층 │ 이름        │ 역할              │ PDU     │ 장비/프로토콜
  ─────┼────────────┼──────────────────┼────────┼───────────────
  7    │ 응용        │ 사용자 인터페이스   │ 메시지  │ HTTP, DNS, SMTP
  6    │ 표현        │ 데이터 형식 변환   │         │ SSL/TLS, JPEG
  5    │ 세션        │ 연결 관리          │         │ NetBIOS
  4    │ 전송        │ 종단간 신뢰성      │ 세그먼트 │ TCP, UDP
  3    │ 네트워크    │ 라우팅, 주소 지정   │ 패킷    │ IP, ICMP, 라우터
  2    │ 데이터링크  │ 프레임 전송, 오류   │ 프레임   │ Ethernet, 스위치
  1    │ 물리        │ 비트 전송          │ 비트    │ 케이블, 허브

TCP/IP 4계층 (실제 인터넷):

  응용 계층      ← OSI 5,6,7 통합
  전송 계층      ← OSI 4
  인터넷 계층    ← OSI 3
  네트워크 접근  ← OSI 1,2 통합

왜 두 모델이 있는가:
  OSI: "이론적으로 깔끔한 분류". 교육·참조용.
  TCP/IP: "실제로 인터넷이 이렇게 작동". 구현 중심.
  현실에서는 TCP/IP가 표준이지만, 설명할 때 OSI 7계층을 참조한다.
```

### 1.3 캡슐화 — 편지 봉투의 원리

```
🔴 [원리] 캡슐화 (Encapsulation):
  데이터가 각 계층을 내려갈 때마다 해당 계층의 헤더가 추가된다.

  응용:  [HTTP 데이터                              ]
  전송:  [TCP 헤더][HTTP 데이터                     ]
  네트워크:[IP 헤더][TCP 헤더][HTTP 데이터             ]
  링크:  [Eth 헤더][IP 헤더][TCP 헤더][HTTP 데이터][Eth Trailer]

  받는 쪽에서는 각 계층이 자기 헤더를 벗기고 위 계층에 전달 (역캡슐화).

  왜 이렇게 하는가:
    각 계층은 자기 헤더만 읽고, 안의 내용은 신경 쓰지 않는다.
    → 계층 간 독립성 보장!
    IP는 TCP인지 UDP인지 상관없이 패킷을 전달한다.
```

## 2. 데이터링크 계층 — "바로 옆에 전달"

```
🔴 역할: 직접 연결된 두 장치 사이에서 프레임을 전달한다.

MAC 주소: 48비트 하드웨어 주소 (예: AA:BB:CC:DD:EE:FF)
  NIC(네트워크 카드)에 고유하게 할당. "하드웨어의 주민번호".
  
  IP 주소와의 차이:
    MAC: 물리적, 변경 불가(원칙), 같은 네트워크 내에서만 의미
    IP: 논리적, 변경 가능, 전 세계적으로 유일한 주소

이더넷 (IEEE 802.3):
  유선 LAN의 사실상 표준.
  CSMA/CD: 충돌 감지 — 송신 전 회선 확인, 충돌 시 랜덤 대기 후 재전송.
  현대 스위치: 풀 듀플렉스(동시 송수신) → 충돌이 거의 안 일어남 → CSMA/CD 비활성화.

스위치:
  MAC 주소 학습 → 목적지 MAC이 있는 포트로만 프레임 전달.
  허브(모든 포트에 뿌림)와 달리, 필요한 곳에만 전달 → 효율적.

ARP (Address Resolution Protocol):
  "이 IP 주소를 가진 장치의 MAC 주소가 뭐야?"
  → 브로드캐스트로 질문, 해당 장치가 자기 MAC을 응답.
  → IP와 MAC 사이의 번역기.
```

## 3. 네트워크 계층 — "어디로 보낼 것인가"

### 3.1 IP 주소와 서브넷팅

```
🔴 IPv4: 32비트 주소. 점으로 구분된 4개 옥텟.
  예: 192.168.1.100 = 11000000.10101000.00000001.01100100

  서브넷 마스크: 네트워크 부분과 호스트 부분을 구분.
  CIDR 표기: 192.168.1.0/24 = 앞 24비트가 네트워크, 뒤 8비트가 호스트.
  
  /24이면: 2⁸ - 2 = 254개 호스트 가능 (0은 네트워크 주소, 255는 브로드캐스트)

왜 서브넷팅이 필요한가:
  하나의 거대 네트워크보다 작은 네트워크 여러 개가 관리하기 쉽다.
  브로드캐스트 범위를 줄여 성능 향상.
  부서/건물/층별로 네트워크를 분리하여 보안 강화.

🔴 IPv6: 128비트 주소. IPv4 주소 고갈 문제 해결.
  예: 2001:0db8:85a3:0000:0000:8a2e:0370:7334
  2¹²⁸ ≈ 3.4 × 10³⁸개 주소 → 지구의 모래알 수보다 많다.
```

### 3.2 라우팅 — 패킷이 목적지를 찾아가는 방법

```
🔴 [원리] 라우팅: 패킷이 출발지에서 목적지까지 가는 경로를 결정하는 것.

라우팅 테이블: 각 라우터가 "이 목적지로 가려면 어느 이웃에게 보내라"를 기록.

라우팅 프로토콜 — 왜 여러 가지인가:

  (1) 거리 벡터 (Distance Vector) — RIP:
    각 라우터가 이웃에게 자기의 라우팅 테이블을 공유.
    벨만-포드 알고리즘 기반 (Ch.10).
    단순하지만 수렴이 느리고, 최대 15홉 제한.

  (2) 링크 상태 (Link State) — OSPF:
    각 라우터가 자기 이웃과의 연결 상태를 전체 네트워크에 알림.
    모든 라우터가 전체 토폴로지를 파악 → 다익스트라(Ch.10)로 최단 경로 계산.
    빠른 수렴, 대규모 네트워크에 적합.

  (3) 경로 벡터 (Path Vector) — BGP:
    인터넷의 AS(자율 시스템) 간 라우팅.
    경로 정보(어떤 AS를 거치는가)를 공유 → 루프 방지.
    정책 기반 (비용, 정치적 관계 등).
    → BGP가 인터넷의 "백본 라우팅". 인터넷을 하나로 묶는 프로토콜.

  각각의 존재 이유:
    RIP: 소규모 네트워크에서 단순하게
    OSPF: 한 조직 내부의 대규모 네트워크
    BGP: 조직 간, 인터넷 전체
    → 규모와 정책 요구가 다르면 프로토콜도 달라야 한다.

🔴 NAT (Network Address Translation):
  사설 IP ↔ 공인 IP 변환.
  왜 필요한가: IPv4 주소가 부족. 사설 주소(192.168.x.x 등)를 내부에서 쓰고,
  외부와 통신할 때만 공인 IP로 변환 → 적은 공인 IP로 많은 장치 연결.
```

## 4. 전송 계층 — "신뢰성 있는 종단간 통신"

### 4.1 TCP — 왜 이렇게 복잡한가

```
🔴 [정의] TCP: 연결 지향, 신뢰성 보장, 흐름/혼잡 제어를 제공하는 프로토콜.

왜 복잡한가:
  IP는 "최선형(best-effort)" — 패킷이 유실/중복/순서 바뀜이 가능.
  TCP는 이 위에서 "반드시 정확하게 순서대로 도착"을 보장해야 한다.
  → 유실 감지·재전송, 순서 재조립, 흐름 제어, 혼잡 제어가 필요.
```

**3-way Handshake — 왜 3번인가:**

```
🔴 TCP 연결 수립:

  클라이언트              서버
      │──── SYN ────→│        "연결하자" (나의 시작 번호: x)
      │                │
      │←── SYN+ACK ──│        "좋아, 연결하자" (나의 시작 번호: y, 너의 x 확인)
      │                │
      │──── ACK ────→│        "확인했어" (너의 y 확인)
      │                │
      연결 수립!

왜 2번이 아니라 3번인가:
  2번이면 서버가 "클라이언트가 자기 ACK을 받았는지" 모른다.
  
  시나리오: 클라이언트의 오래된 SYN이 지연 도착 → 서버가 SYN+ACK 응답
  → 클라이언트는 이미 연결을 포기한 상태 → 서버만 혼자 연결 상태로 대기
  
  3번째 ACK이 있으면:
    클라이언트가 응답하지 않으면 → 서버가 연결을 해제할 수 있다.
    → "양쪽 모두 합의"를 보장하기 위해 최소 3번 필요.
```

**TCP 흐름 제어 — 왜 윈도우인가:**

```
🔴 슬라이딩 윈도우 (Sliding Window):
  수신자가 "나는 최대 W바이트까지 받을 수 있어"라고 알려줌.
  송신자는 W바이트 이내에서 ACK 없이 연속 전송.

  왜 한 번에 하나씩 보내면 안 되는가:
    패킷 전송 → ACK 대기 → 다음 패킷 → ...
    RTT(왕복 시간)이 100ms이면 → 초당 10 패킷 = 매우 느림!
    
    윈도우: ACK을 기다리지 않고 여러 패킷을 연속으로 보냄.
    → 파이프라인처럼 네트워크를 채운다 → 처리량 극대화.
```

**TCP 혼잡 제어 — 왜 필요한가:**

```
🔴 혼잡 제어: "네트워크가 감당할 수 있는 양만 보내자"

  모든 송신자가 마음대로 전송하면 → 네트워크 과부하 → 패킷 유실 폭증 → 재전송 폭증
  → 더 심한 혼잡 → 붕괴! (Congestion Collapse)

  단계:
  (1) Slow Start: cwnd = 1에서 시작, ACK마다 2배 (지수 증가)
      왜 1에서 시작: 네트워크 상태를 모르므로 조심스럽게 시작.
      왜 지수 증가: 빠르게 적절한 속도를 찾기 위해.

  (2) Congestion Avoidance: ssthresh 도달 후 선형 증가 (+1씩)
      왜 선형: 혼잡에 가까우므로 조심스럽게 증가.

  (3) 손실 감지 시:
      타임아웃 → cwnd = 1, ssthresh = cwnd/2 (처음부터 다시)
      3중복 ACK → cwnd = cwnd/2 (Fast Recovery, 절반으로 줄이고 계속)

  시각화 (cwnd 변화):

  cwnd
    │        ╱╲
    │      ╱    ╲     ← 손실! cwnd 절반
    │    ╱        ──────╱╲
    │  ╱  Slow      CA      ╲ 
    │╱   Start                ╲
    ┼──────────────────────────── 시간
       지수증가   선형증가    손실→감소

🔵 [CS 연결] TCP 혼잡 제어가 인터넷이 작동하는 핵심 이유:
  모든 송신자가 이 프로토콜을 따르면 → 네트워크를 공정하게 공유.
  따르지 않으면 → 일부가 독점 → 나머지가 굶음.
```

### 4.2 UDP — 왜 TCP만으로는 부족한가

```
🔴 UDP: 비연결, 비신뢰성, 최소 오버헤드.
  헤더: 8바이트 (TCP: 20바이트)
  핸드셰이크 없음, 재전송 없음, 흐름/혼잡 제어 없음.

왜 이런 "불완전한" 프로토콜이 필요한가:

  실시간 통신: 지연이 재전송보다 나쁘다!
    영상 통화에서 1초 전 프레임을 재전송받아봤자 무의미.
    약간의 화질 저하가 끊김(재전송 대기)보다 낫다.

  🔵 UDP 사용 사례:
    DNS: 짧은 질의-응답. 연결 오버헤드가 비쌈.
    스트리밍: 약간의 유실은 OK.
    온라인 게임: 최신 상태가 중요, 과거 프레임 재전송 불필요.
    VoIP: 실시간 음성.
    QUIC: HTTP/3의 기반. UDP 위에 사용자 공간 프로토콜을 구축.

  QUIC (HTTP/3):
    UDP 위에 TCP의 장점(신뢰성, 혼잡 제어)을 사용자 공간에서 구현.
    왜: TCP는 OS 커널에 있어서 업그레이드가 느리다. 
    UDP 위에 새 프로토콜을 만들면 → 앱 업데이트만으로 프로토콜 개선 가능!
```

## 5. 응용 계층 — 사용자가 실제로 만나는 프로토콜

### 5.1 HTTP — 웹의 언어

```
🔴 HTTP (HyperText Transfer Protocol):
  요청-응답(request-response) 모델. 상태 없음(stateless).

  요청:  GET /index.html HTTP/1.1
         Host: www.example.com

  응답:  HTTP/1.1 200 OK
         Content-Type: text/html
         
         <html>...</html>

🔴 HTTP 메서드의 의미:
  GET:    자원 조회 (읽기)
  POST:   자원 생성 (쓰기)
  PUT:    자원 전체 교체
  PATCH:  자원 부분 수정
  DELETE: 자원 삭제

🔴 상태 코드:
  2xx: 성공 (200 OK, 201 Created)
  3xx: 리다이렉트 (301 영구 이동, 304 수정 안 됨)
  4xx: 클라이언트 오류 (400 잘못된 요청, 403 금지, 404 없음)
  5xx: 서버 오류 (500 내부 오류, 503 서비스 불가)

HTTP의 진화:
  HTTP/1.0: 요청마다 TCP 연결 생성/종료 → 비효율
  HTTP/1.1: 지속 연결(keep-alive). 파이프라이닝. → 현재도 널리 사용
  HTTP/2:   멀티플렉싱(하나의 연결에 여러 요청 동시), 헤더 압축, 서버 푸시
  HTTP/3:   QUIC 기반(UDP). 연결 설정이 더 빠름. 패킷 손실 시 다른 스트림 영향 없음.
```

### 5.2 DNS — "이름을 주소로"

```
🔴 DNS: 도메인 이름 → IP 주소 변환

  www.google.com → 142.250.196.100

왜 DNS가 필요한가:
  사람은 이름을 잘 기억하고, 컴퓨터는 숫자(IP)로 통신한다.
  → DNS = 인터넷의 전화번호부.

계층 구조:
  . (루트) → .com (TLD) → google.com → www.google.com

  Root DNS → TLD DNS → Authoritative DNS

  질의 과정:
  (1) 브라우저: "www.google.com의 IP는?" → 로컬 DNS 서버
  (2) 로컬 DNS → 루트 DNS: ".com은 어디서 관리해?" → TLD DNS 주소 반환
  (3) 로컬 DNS → TLD DNS: "google.com은?" → Authoritative DNS 주소 반환
  (4) 로컬 DNS → Authoritative DNS: "www.google.com은?" → IP 반환
  (5) 결과 캐싱 (TTL 동안)

  왜 분산 계층 구조인가:
    중앙 서버 하나면 → 단일 장애점 + 전 세계 트래픽 집중
    분산하면 → 부하 분산 + 장애 격리 + 로컬 캐시로 속도 향상

🔵 DNS 캐싱:
  한번 조회한 결과를 TTL 동안 저장.
  대부분의 DNS 질의는 캐시에서 해결 → 매우 빠름.
```

### 5.3 DHCP — "자동으로 IP 받기"

```
🔴 DHCP: IP 주소, 서브넷 마스크, 게이트웨이, DNS 서버를 자동 할당.

  4단계:
  (1) Discover: 클라이언트가 브로드캐스트 "DHCP 서버 있나요?"
  (2) Offer: 서버가 "이 IP 쓸래요?"
  (3) Request: 클라이언트가 "네, 그거 주세요"
  (4) ACK: 서버가 "확인, 이제 당신 거예요"

  왜 4단계: DHCP 서버가 여러 개일 수 있으므로,
  Offer를 받고 → Request로 하나를 선택 → ACK으로 확정.
```

## 6. 소켓 프로그래밍 — 네트워크의 API

```
🔴 소켓(Socket): 네트워크 통신의 끝점. (IP 주소, 포트 번호)의 쌍.

  포트 번호: 같은 IP의 어떤 프로세스와 통신하는지 구분.
    Well-known: 0~1023 (HTTP=80, HTTPS=443, SSH=22, DNS=53)
    등록:       1024~49151
    동적:       49152~65535

TCP 서버-클라이언트 흐름:

  서버:                       클라이언트:
  socket()                    socket()
  bind(주소, 포트)
  listen()
  accept() ← 연결 대기 ───── connect()
  recv()/send()               send()/recv()
  close()                     close()

🔵 [CS 연결]
  모든 네트워크 프로그램(웹 서버, 채팅, 게임)의 기반.
  고수준 프레임워크(Flask, Express, Spring)도 내부적으로 소켓을 사용.
```

## 8. 정리

```
[원리 1] 계층화: 복잡한 문제를 독립적 계층으로 분리. 각 계층은 아래 계층의 서비스를 사용.
[원리 2] 캡슐화: 각 계층이 헤더를 추가하며, 위 계층의 내용은 건드리지 않는다.
[원리 3] TCP의 신뢰성: 순서 보장 + 재전송 + 흐름/혼잡 제어 = 불완전한 IP 위에 완전한 통신.
[원리 4] UDP의 단순함: 오버헤드 최소화 → 실시간/경량 통신에 적합.
[원리 5] 라우팅: 분산된 라우터들이 협력하여 경로를 결정. 알고리즘(벨만-포드, 다익스트라)이 핵심.
[원리 6] DNS: 분산 계층 구조 + 캐싱 → 확장성과 속도.

외워야 할 것:
  🔴 OSI 7계층 (이름, 역할, PDU, 대표 프로토콜)
  🔴 TCP 3-way handshake (SYN → SYN+ACK → ACK)
  🔴 TCP vs UDP 차이
  🔴 HTTP 메서드와 상태 코드 체계
  🔴 IP 주소 체계와 서브넷 마스크 (CIDR)
  🔴 DNS 계층 구조와 질의 과정
```
