## 0.5 이 챕터에서 만나는 기호와 읽는 법

```
┌──────────────┬──────────────────────────┬──────────────────────────────────┐
│ 기호          │ 읽는 법                   │ 의미                              │
├──────────────┼──────────────────────────┼──────────────────────────────────┤
│ O(f(n))      │ "빅 오 에프 엔"           │ 최악의 경우 상한 (최대 이만큼)      │

│ O(n log n)   │ "오 엔 로그 엔"           │ 효율적 정렬의 복잡도               │
│ O(n²)        │ "오 엔 제곱"             │ 이중 루프                         │
│ amortized    │ "어모타이즈드"            │ 분할 상환 분석 (평균적 관점)         │
│ n            │ "엔"                    │ 데이터의 개수 (입력 크기)            │
│ h            │ "에이치"                 │ 트리의 높이 (height)               │
│ k            │ "케이"                   │ 상수 또는 매개변수                  │
│ α            │ "알파"                   │ 부하율 (load factor) — 해시에서     │
│ null, nil    │ "널" 또는 "닐"           │ 아무것도 가리키지 않는 포인터        │
│ →            │ "가리킨다" 또는 "포인터"   │ 연결 리스트에서 다음 노드 참조       │

└──────────────┴──────────────────────────┴──────────────────────────────────┘
```

## 1. 출발점: 자료구조는 왜 존재하는가

### 1.1 핵심 질문

```
자료구조의 존재 이유는 단 하나의 질문에서 출발한다:

  "데이터를 어떻게 정리해두면, 원하는 연산을 가장 빠르게 할 수 있는가?"

책장 비유:
  - 책을 바닥에 쌓아두면? → 찾기 O(n), 넣기 O(1)
  - 제목순으로 꽂으면? → 찾기 O(log n), 넣기 O(n) (빈 자리를 만들어야)
  - 알파벳 첫 글자별 구역? → 찾기 빠름, 구역 관리 필요

  → 같은 데이터도 정리 방법에 따라 연산 속도가 극적으로 달라진다.
  → 자료구조 = "데이터의 정리 방법"
```

### 1.2 핵심 트레이드오프 — 왜 "만능 자료구조"는 없는가

```
🔴 [원리] 모든 자료구조에는 트레이드오프가 있다.

  한 연산을 빠르게 만들면, 다른 연산이 느려진다.

  ┌───────────┬──────────────┬──────────────┐
  │ 빠르게 하고 │ 대가로        │ 예시          │
  │ 싶은 연산   │ 느려지는 연산  │              │
  ├───────────┼──────────────┼──────────────┤
  │ 검색       │ 삽입/삭제     │ 정렬된 배열    │
  │ 삽입/삭제   │ 검색         │ 연결 리스트    │
  │ 모든 연산   │ 메모리 사용   │ 해시 테이블    │
  │ 범위 검색   │ 구현 복잡도   │ 균형 이진 트리  │
  └───────────┴──────────────┴──────────────┘

  "무엇을 자주 하느냐"에 따라 최적의 자료구조가 달라진다.
  → 자료구조 선택 = 문제의 연산 패턴 분석 + 트레이드오프 결정
```

### 1.3 ADT vs 자료구조 — 구분이 왜 중요한가

```
🔴 [정의]
  추상 자료형 (ADT, Abstract Data Type):
    "무엇을 할 수 있는가" — 연산의 명세 (인터페이스)
    예: 스택 ADT = push, pop, peek, isEmpty

  자료구조 (Data Structure):
    "어떻게 구현하는가" — 메모리에서의 실제 구조
    예: 스택을 배열로 구현, 연결 리스트로 구현

  하나의 ADT를 여러 자료구조로 구현할 수 있다.
  
  Map ADT = { get(key), put(key,value), delete(key) }
    → 구현: 해시 테이블, BST, 정렬 배열, 연결 리스트 ...
    → 각 구현마다 연산의 시간 복잡도가 다르다

🔵 [CS 연결] 
  Java: interface Map<K,V> (ADT) → HashMap, TreeMap, LinkedHashMap (구현)
  Python: dict (해시 테이블 기반), collections.OrderedDict
  이 구분이 "인터페이스와 구현의 분리" 원칙의 기원이다.
```

## 2. 배열 — 가장 원시적이지만 가장 강력한 구조

### 2.1 배열이란 — 왜 인덱스 접근이 O(1)인가

```
🔴 [정의] 배열: 동일 타입의 원소가 메모리에 연속으로 저장된 구조

  메모리:
  주소: 100  104  108  112  116  120
       ┌────┬────┬────┬────┬────┬────┐
       │ 10 │ 20 │ 30 │ 40 │ 50 │ 60 │
       └────┴────┴────┴────┴────┴────┘
  인덱스: [0]  [1]  [2]  [3]  [4]  [5]

왜 A[i] 접근이 O(1)인가:
  주소 계산: A[i]의 주소 = 시작주소 + i × (원소 크기)
  
  A[3]의 주소 = 100 + 3 × 4 = 112
  
  덧셈과 곱셈 하나씩이면 끝. 입력 크기 n에 무관.
  → O(1) 랜덤 접근!
  
  이것이 가능한 이유: "연속 메모리 + 동일 크기 원소"
  이 두 조건이 깨지면 O(1) 접근이 불가능하다.

🔵 [CS 연결]
  CPU 캐시 친화적: 연속 메모리 → 공간 지역성(spatial locality) 극대화
  → 배열 순회는 캐시 히트율이 높아 실제로 매우 빠르다
  → 이론적 복잡도가 같아도, 배열이 연결 리스트보다 실제로 빠른 이유
```

### 2.2 배열의 트레이드오프

```
  접근: O(1) — 최고  ← 연속 메모리 + 인덱스 산술 덕분
  검색: O(n) — 정렬 안 됐으면 처음부터 끝까지 봐야 함
       O(log n) — 정렬됐으면 이진 탐색 가능
  삽입: O(n) — 중간에 넣으려면 뒤의 원소를 모두 이동
  삭제: O(n) — 빈 자리를 메우려면 이동 필요

  삽입/삭제가 느린 이유:
    연속 메모리를 유지해야 하므로, 원소를 밀고 당겨야 한다.
    
    [10, 20, 30, 40, 50]에 25를 인덱스 2에 삽입:
    
    Step 1: 뒤로 밀기  [10, 20, __, 30, 40, 50]
    Step 2: 삽입       [10, 20, 25, 30, 40, 50]
    
    최악의 경우 n개를 모두 이동 → O(n)
```

### 2.3 동적 배열 — 크기 제한을 어떻게 해결하는가

```
정적 배열은 크기가 고정. 동적 배열은 자동으로 늘어난다.

🔴 [핵심 전략] 더블링 (Doubling):
  배열이 가득 차면, 2배 크기의 새 배열을 할당하고 복사한다.

  왜 2배인가:
    n번 삽입의 총 비용을 분석하면:
    
    복사 발생: 크기 1→2→4→8→...→n
    복사 비용: 1 + 2 + 4 + 8 + ... + n = 2n - 1
    
    n번 삽입에 대해 총 비용 ≈ 3n → 삽입 하나당 평균 O(1)
    
    이것이 "분할 상환 분석 (amortized analysis)"이다:
    가끔 O(n) 복사가 발생하지만, 이를 모든 삽입에 분산하면 평균 O(1).

    1.5배로 늘리면? → 여전히 amortized O(1), 메모리 낭비 감소
    Java ArrayList = 1.5배, Python list = ~1.125배, C++ vector = 2배

🔵 [CS 연결]
  Python의 list, Java의 ArrayList, C++의 std::vector
  모두 동적 배열이다. append/push_back이 amortized O(1)인 이유가 이것.
```

## 3. 연결 리스트 — 삽입/삭제의 자유

### 3.1 연결 리스트란 — 배열과 정반대의 트레이드오프

```
🔴 [정의] 각 노드가 데이터 + 다음 노드의 포인터(주소)를 가진 구조

  단일 연결 리스트:
  ┌───┬───┐    ┌───┬───┐    ┌───┬───┐    ┌───┬──────┐
  │ 10│ →─┼──→ │ 20│ →─┼──→ │ 30│ →─┼──→ │ 40│ null │
  └───┴───┘    └───┴───┘    └───┴───┘    └───┴──────┘
  head                                      tail

왜 삽입/삭제가 O(1)인가:
  "포인터만 바꾸면 된다" — 원소를 이동할 필요 없다!

  20 뒤에 25 삽입:
  Before: 20 → 30
  After:  20 → 25 → 30  (포인터 2개만 변경)

  20 삭제:
  Before: 10 → 20 → 30
  After:  10 → 30  (10의 포인터를 30으로 변경)

왜 접근이 O(n)인가:
  메모리가 연속이 아니므로 주소 산술이 불가.
  i번째 원소를 찾으려면 head부터 i번 따라가야 한다.
```

### 3.2 연결 리스트의 변형

```
이중 연결 리스트 (Doubly Linked List):
  각 노드가 prev와 next 포인터를 모두 가짐.
  → 양방향 순회 가능, 특정 노드의 삭제가 O(1)
     (단일에서는 이전 노드를 모르므로 삭제에 O(n) 탐색 필요)

  ┌──────┬───┬──────┐    ┌──────┬───┬──────┐
  │ null │10 │  →───┼──→ │ ←──  │20 │  →───┼──→ ...
  └──────┴───┴──────┘    └──────┴───┴──────┘
           prev data next

원형 연결 리스트 (Circular):
  마지막 노드의 next가 head를 가리킴.
  → "끝"이 없는 순환 구조

🔵 [CS 연결]
  OS의 프로세스 관리: 원형 연결 리스트로 라운드 로빈 스케줄링
  브라우저의 앞/뒤로 가기: 이중 연결 리스트
  Java의 LinkedList: 이중 연결 리스트
  LRU 캐시: 해시 테이블 + 이중 연결 리스트의 조합
```

### 3.3 배열 vs 연결 리스트 — 언제 무엇을 쓰는가

```
┌───────────────┬──────────┬───────────────┐
│ 연산           │ 배열      │ 연결 리스트     │
├───────────────┼──────────┼───────────────┤
│ 인덱스 접근    │ O(1) ★   │ O(n)          │
│ 검색 (비정렬)  │ O(n)     │ O(n)          │
│ 맨 앞 삽입     │ O(n)     │ O(1) ★        │
│ 맨 뒤 삽입     │ O(1)*    │ O(1) (tail有)  │
│ 중간 삽입      │ O(n)     │ O(1) (위치 알면)│
│ 삭제          │ O(n)     │ O(1) (노드 알면)│
│ 캐시 효율      │ 높음 ★   │ 낮음           │
│ 메모리 오버헤드 │ 낮음     │ 높음 (포인터)   │
└───────────────┴──────────┴───────────────┘
 * 동적 배열의 amortized O(1)

실용 지침:
  대부분의 경우 배열(동적 배열)이 낫다. 캐시 효율 때문.
  연결 리스트가 필요한 경우:
    - 맨 앞 삽입/삭제가 매우 빈번
    - 데이터 크기가 매우 크고 이동 비용이 높을 때
    - 다른 자료구조의 내부 구현 (LRU 캐시, 해시 체이닝 등)
```

## 4. 스택과 큐 — 접근 순서를 제한하는 이유

### 4.1 스택 — 왜 "제한"이 유용한가

```
🔴 [정의] 스택 (Stack): LIFO (Last In, First Out)
  연산: push(추가), pop(제거+반환), peek(확인), isEmpty
  모두 O(1)

  push 3, push 7, push 1:        pop:
  ┌───┐                          ┌───┐
  │ 1 │ ← top                    │ 7 │ ← top (1이 나감)
  ├───┤                          ├───┤
  │ 7 │                          │ 3 │
  ├───┤                          └───┘
  │ 3 │
  └───┘

왜 자유로운 접근을 "제한"하는가:
  제한 = 보장.
  "가장 최근 것만 처리한다"는 제한이 많은 문제를 자연스럽게 해결한다.

🔵 [CS 연결]
  함수 호출 스택: main → f() → g() → g 리턴 → f 리턴 → main
    가장 나중에 호출된 함수가 가장 먼저 리턴 = LIFO
    
  괄호 매칭: ( ( ) ( ) )
    '(' 만나면 push, ')' 만나면 pop, 끝에 스택이 비면 올바른 괄호
    
  Undo 기능: 가장 최근 동작을 먼저 되돌림 = LIFO
  
  DFS (깊이 우선 탐색): 재귀 = 암시적 스택, 명시적으로도 스택 사용
  
  후위 표기식 계산: 3 4 + 5 × = (3+4)×5 = 35
    숫자 → push, 연산자 → pop 2개, 계산, 결과 push
```

### 4.2 큐 — 선입선출

```
🔴 [정의] 큐 (Queue): FIFO (First In, First Out)
  연산: enqueue(추가), dequeue(제거+반환), peek, isEmpty
  모두 O(1)

  enqueue 3, 7, 1:              dequeue:
  front → │ 3 │ 7 │ 1 │ ← rear  front → │ 7 │ 1 │ ← rear (3이 나감)

왜 FIFO인가:
  "먼저 온 것을 먼저 처리" — 공정함의 원칙

🔵 [CS 연결]
  BFS (너비 우선 탐색): 가까운 노드부터 처리 = FIFO
  프로세스 스케줄링: FCFS(First Come First Served)
  프린터 대기열, 메시지 큐(Kafka, RabbitMQ)
  네트워크 패킷 버퍼

덱 (Deque, Double-Ended Queue):
  양쪽 끝에서 삽입/삭제 가능.
  스택과 큐를 모두 대체할 수 있다.
  Python의 collections.deque
```

### 4.3 우선순위 큐 — "가장 중요한 것 먼저"

```
🔴 [ADT] 우선순위 큐:
  insert(value, priority), extractMin/extractMax
  
  FIFO가 아니라, 우선순위가 높은 것이 먼저 나온다.

구현은 힙(§6)이 최적이다.

🔵 [CS 연결]
  다익스트라 최단 경로: 가장 가까운 미방문 노드 선택 → 최소 힙
  작업 스케줄링: 우선순위 기반 프로세스 관리
  허프만 코딩: 가장 빈도 낮은 두 노드 합치기 → 최소 힙
  A* 경로 탐색: 가장 유망한 노드 선택 → 우선순위 큐
```

## 5. 해시 테이블 — "거의 O(1)"의 비밀

### 5.1 해시 테이블이란 — 왜 이것이 마법처럼 빠른가

```
🔴 [핵심 아이디어]
  키(key)를 해시 함수로 "주소"로 변환하여, 그 주소에 값을 저장한다.
  → 키로부터 주소를 직접 계산 → O(1) 접근!

  해시 함수: h(key) → index (0 ~ m-1)

  key = "alice" → h("alice") = 3 → 테이블[3]에 저장
  key = "bob"   → h("bob") = 7   → 테이블[7]에 저장

  검색: h("alice") = 3 → 테이블[3] 확인 → O(1)!

왜 O(1)인가:
  해시 함수 계산 = O(키 길이) ≈ O(1) (키 길이가 상수면)
  배열 인덱스 접근 = O(1)
  합계 = O(1)

문제: 충돌(collision) — 다른 키가 같은 인덱스를 받을 때
  h("alice") = 3, h("charlie") = 3이면?
  → 같은 칸에 두 개가 들어가야 한다!
  → 충돌은 비둘기집 원리에 의해 불가피하다 (Ch.04)
     (키의 수 > 테이블 크기이면 반드시 발생)
```

### 5.2 충돌 해결 — 두 가지 전략

```
🔴 [전략 1] 체이닝 (Chaining):
  각 버킷에 연결 리스트를 둔다. 같은 인덱스의 키들을 리스트로 연결.

  index 0: → null
  index 1: → ("bob", 25) → null
  index 2: → null
  index 3: → ("alice", 30) → ("charlie", 22) → null
  index 4: → null

  검색: h(key) 계산 → 해당 리스트를 순회
  최악: 모든 키가 같은 버킷 → O(n) 리스트 순회
  평균: 부하율 α = n/m일 때, 리스트 길이 ≈ α → O(1+α) ≈ O(1)

🔴 [전략 2] 개방 주소법 (Open Addressing):
  충돌 시 다른 빈 칸을 찾아간다.

  선형 탐사: h(k), h(k)+1, h(k)+2, ...
    장점: 캐시 친화적 (연속 메모리 접근)
    단점: 클러스터링 — 채워진 영역이 뭉치면 성능 급락

  이차 탐사: h(k), h(k)+1², h(k)+2², ...
    클러스터링 완화

  이중 해싱: h₁(k), h₁(k)+h₂(k), h₁(k)+2·h₂(k), ...
    가장 균등한 분포, 클러스터링 최소

🟢 [유도 가능] 부하율과 성능:
  α = n/m (저장된 원소 수 / 테이블 크기)
  
  α가 커지면 → 충돌 증가 → 성능 저하
  보통 α > 0.7~0.75이면 테이블을 2배로 확장(rehashing)
  
  Python dict: α ≈ 2/3에서 리사이징
  Java HashMap: α = 0.75에서 리사이징
```

### 5.3 좋은 해시 함수란 — 왜 이것이 중요한가

```
해시 테이블의 성능은 해시 함수의 품질에 달려 있다.

좋은 해시 함수의 조건:
  (1) 균등 분포: 키를 테이블 전체에 고르게 분산
  (2) 결정적: 같은 키 → 항상 같은 해시값
  (3) 빠른 계산: O(키 길이) 이내

왜 균등 분포가 중요한가:
  편향되면 특정 버킷에 몰림 → 체인이 길어짐 → O(n)에 가까워짐
  균등하면 체인 길이 ≈ α → O(1)에 가까움

🔵 [CS 연결]
  암호학적 해시 (SHA-256): 균등 + 역상 저항 + 충돌 저항 → Ch.14 보안
  비암호학적 해시 (MurmurHash, FNV): 빠르고 균등, 해시 테이블용
  
  해시의 진짜 마법:
    임의의 데이터 → 고정 크기 숫자 변환
    이 변환이 균등하면, "주소 검색 없이 바로 찾기"가 가능
```

## 6. 힙 — 우선순위 큐의 최적 구현

### 6.1 힙이란 — 왜 이 구조인가

```
🔴 [정의] (이진) 최소 힙 (Min Heap):
  (1) 완전 이진 트리 (마지막 레벨 제외 모든 레벨이 가득 참)
  (2) 힙 성질: 부모 ≤ 자식 (모든 노드에서)

         1
       ╱   ╲
      3      5
     ╱ ╲   ╱
    7   4  8

  루트가 항상 최소값!

왜 "완전 이진 트리"인가:
  배열로 구현할 수 있다! 포인터가 필요 없다.
  
  인덱스 관계 (0-based):
    부모:     ⌊(i-1)/2⌋
    왼쪽 자식: 2i + 1
    오른쪽 자식: 2i + 2

  배열: [1, 3, 5, 7, 4, 8]
         ↑  ↑  ↑  ↑  ↑  ↑
         0  1  2  3  4  5

  왜 이 인덱스 공식이 성립하는가:
    완전 이진 트리를 레벨별로 왼쪽부터 번호를 매기면,
    부모-자식 관계가 정확히 이 산술식이 된다.
    이진 트리의 "각 레벨이 이전 레벨의 2배" 성질에서 자연스럽게 나온다.
```

### 6.2 힙 연산 — 왜 O(log n)인가

```
🟢 [유도 가능]

  insert (삽입): O(log n)
    1. 배열 끝에 추가 (완전 트리 유지)
    2. "위로 떠오르기(bubble up)": 부모보다 작으면 교환, 반복
    → 최대 트리 높이만큼 올라감 = O(log n)

  extractMin (최소값 추출): O(log n)
    1. 루트(최소값) 반환
    2. 배열 마지막 원소를 루트로 이동
    3. "아래로 내려가기(bubble down)": 자식 중 작은 것과 교환, 반복
    → 최대 트리 높이만큼 내려감 = O(log n)

  왜 O(log n)인가:
    완전 이진 트리의 높이 = ⌊log₂ n⌋
    삽입/삭제 모두 "한 경로만 따라감" → O(높이) = O(log n)

  heapify (배열 → 힙 변환): O(n)  ← O(n log n)이 아니다!
    왜 O(n)인가:
    바닥 레벨의 노드는 내려갈 곳이 없고 (0 비용),
    높은 레벨의 노드는 적지만 많이 내려가야 하고,
    낮은 레벨의 노드는 많지만 조금만 내려가면 된다.
    총 합을 계산하면 O(n). (기하급수의 합으로 유도)
```

## 7. 이진 탐색 트리 (BST) — 정렬 + 유연성

### 7.1 BST란 — 왜 이 규칙인가

```
🔴 [정의] 이진 탐색 트리 (BST):
  모든 노드에서: 왼쪽 서브트리의 모든 값 < 노드 값 < 오른쪽 서브트리의 모든 값

         8
       ╱   ╲
      3     10
     ╱ ╲      ╲
    1   6     14
       ╱ ╲   ╱
      4   7  13

왜 이 규칙인가:
  이진 탐색(binary search)의 원리를 트리에 적용한 것.
  
  배열의 이진 탐색: 중간값과 비교 → 왼쪽 또는 오른쪽 절반 선택
  BST: 노드값과 비교 → 왼쪽 또는 오른쪽 서브트리 선택
  
  매 비교마다 탐색 범위가 절반으로 줄어든다 → O(log n)

BST의 트레이드오프 vs 정렬 배열:
  정렬 배열: 검색 O(log n), 삽입 O(n) (밀어야 함)
  BST: 검색 O(log n), 삽입 O(log n) (포인터만 변경!)
  
  → BST = "삽입/삭제가 빠른 정렬 배열"
```

### 7.2 BST의 문제 — 왜 균형이 필요한가

```
문제: BST의 형태가 입력 순서에 의존한다.

  [3, 1, 4, 1, 5, 9]를 순서대로 삽입 → 적당히 균형 잡힌 트리
  [1, 2, 3, 4, 5]를 순서대로 삽입 → 일자로 늘어진 트리!

  균형 BST:         편향 BST (사실상 연결 리스트):
      3               1
     ╱ ╲               ╲
    1    5               2
     ╲  ╱ ╲              ╲
      2 4   9              3
                            ╲
                             4

  균형: 높이 ≈ log n → 모든 연산 O(log n)
  편향: 높이 = n → 모든 연산 O(n) → 배열보다 나을 것이 없다!

→ "자동으로 균형을 유지하는 BST"가 필요하다.
```

### 7.3 균형 BST — AVL과 레드-블랙

```
🔴 [핵심 아이디어] 삽입/삭제 후 자동으로 균형을 복원한다.
  방법: 회전(rotation) — 트리의 구조를 바꾸되 BST 성질은 유지

  왼쪽 회전 (Left Rotation):
    y            x
   ╱ ╲   →     ╱ ╲
  x   C       A   y
 ╱ ╲             ╱ ╲
A   B           B   C

  BST 성질: A < x < B < y < C → 회전 전후 모두 유지!
  높이만 변한다.

AVL 트리:
  규칙: 모든 노드에서 왼쪽/오른쪽 서브트리의 높이 차이 ≤ 1
  위반 시: 회전(1~2번)으로 복원
  보장: 높이 ≤ 1.44 · log₂(n)  → 모든 연산 O(log n)

  왜 1.44인가: 최악의 AVL 트리(가장 높은)는 피보나치 수와 관련.
  높이 h의 최소 노드 수 = F(h+2) ≈ φ^h / √5
  → h ≤ 1.44 log₂(n) 🟢

레드-블랙 트리:
  규칙: 각 노드에 빨강/검정 색을 칠하고, 5가지 규칙을 유지
    (루트는 검정, 빨강의 자식은 검정, 모든 경로의 검정 수 동일 등)
  보장: 높이 ≤ 2 · log₂(n+1)
  
  AVL보다 약간 덜 균형하지만, 삽입/삭제 시 회전이 적다 (최대 3번).
  → 삽입/삭제가 빈번한 경우에 유리.

🔵 [CS 연결]
  Java TreeMap, C++ std::map = 레드-블랙 트리
  리눅스 커널의 스케줄러(CFS) = 레드-블랙 트리
  데이터베이스 인덱스 = 주로 B/B+ 트리 (아래)
```

## 8. B-트리와 B+ 트리 — 디스크를 위한 트리

### 8.1 왜 이진 트리로는 부족한가

```
디스크 접근은 메모리 접근보다 ~100,000배 느리다.
이진 트리의 높이 = log₂(n). n = 10⁶이면 높이 ≈ 20.
매 노드 접근이 디스크 I/O이면 → 20번의 느린 디스크 접근!

해결: 한 노드에 키를 많이 담는다 → 분기 수(branching factor) 증가 → 높이 감소

B-트리: 각 노드에 최대 m개의 키, m+1개의 자식
  m = 1000이면: 높이 = log₁₀₀₀(10⁶) = 2!
  → 20번의 디스크 접근이 2번으로 줄어든다!

🔴 한 노드의 크기 ≈ 디스크 블록 크기 (보통 4KB~16KB)로 맞춘다.
  한 번의 디스크 I/O로 한 노드 전체를 읽는다.
```

### 8.2 B+ 트리 — 왜 DB가 이것을 쓰는가

```
🔴 B+ 트리 = B-트리의 변형:
  - 데이터는 리프(leaf) 노드에만 저장
  - 내부 노드는 키(인덱스)만 저장
  - 리프 노드끼리 연결 리스트로 연결

왜 이것이 DB에 최적인가:
  (1) 내부 노드에 데이터가 없으므로 키를 더 많이 담을 수 있음
      → 분기 수 증가 → 높이 감소 → 디스크 I/O 감소
  
  (2) 리프 노드가 연결되어 있으므로 범위 검색이 효율적
      "나이 20~30인 사람 조회" → 리프를 따라 순회하면 됨
      B-트리에서는 이것이 어렵다

  (3) 모든 검색이 리프까지 가므로 검색 시간이 일정 (예측 가능)

🔵 [CS 연결]
  MySQL InnoDB, PostgreSQL, Oracle = 모두 B+ 트리 인덱스
  파일 시스템 (NTFS, ext4) = B-트리 변형으로 파일 위치 관리
```

## 9. 트라이 (Trie) — 문자열 전용 트리

```
🔴 [정의] 각 간선이 문자(character)를 나타내는 트리.
  루트에서 노드까지의 경로 = 문자열의 접두사(prefix)

  단어: "cat", "car", "card", "do"

         (root)
        ╱      ╲
       c        d
      ╱          ╲
     a            o ★
    ╱ ╲
   t ★  r ★
          ╲
           d ★
  ★ = 단어의 끝 표시

검색: O(m)  (m = 검색 문자열의 길이, 데이터 수 n에 무관!)
삽입: O(m)
접두사 검색: O(m) + 모든 결과 순회

왜 해시 테이블이 아닌 트라이를 쓰는가:
  해시: 정확한 키 매칭만 가능
  트라이: 접두사 매칭 가능! ("car"로 시작하는 모든 단어 검색)

🔵 [CS 연결]
  자동완성: 사용자 입력 접두사 → 트라이에서 가능한 완성 탐색
  IP 라우팅: 가장 긴 접두사 매칭 (longest prefix match)
  맞춤법 검사: 사전을 트라이로 저장
  T9 키보드 입력: 숫자→문자 매핑의 트라이
```

## 10. 그래프 표현 — 관계를 메모리에 담기

### 10.1 인접 행렬 vs 인접 리스트

```
🔴 [두 가지 표현]

  그래프: A—B, A—C, B—C, C—D

  인접 행렬:           인접 리스트:
    A B C D            A: [B, C]
  A 0 1 1 0            B: [A, C]
  B 1 0 1 0            C: [A, B, D]
  C 1 1 0 1            D: [C]
  D 0 0 1 0

  ┌──────────────┬───────────────┬───────────────┐
  │ 기준          │ 인접 행렬      │ 인접 리스트     │
  ├──────────────┼───────────────┼───────────────┤
  │ 공간          │ O(V²)        │ O(V + E)       │
  │ 간선 존재 확인 │ O(1)         │ O(degree)      │
  │ 모든 이웃 순회 │ O(V)         │ O(degree)      │
  │ 적합한 경우    │ 밀집 그래프    │ 희소 그래프     │
  └──────────────┴───────────────┴───────────────┘

왜 대부분 인접 리스트를 쓰는가:
  현실의 그래프는 대부분 희소하다 (E ≪ V²).
  SNS: 10억 사용자, 평균 친구 500명 → E ≈ 500V ≪ V²
  인접 행렬이면 10¹⁸ 공간 필요 → 불가능
  인접 리스트이면 ~5000억 → 어렵지만 가능
```

## 11. 유니온-파인드 (Disjoint Set) — "같은 그룹인가?"

### 11.1 유니온-파인드란

```
🔴 [ADT] 서로소 집합:
  MakeSet(x): x 혼자의 집합 생성
  Find(x): x가 속한 집합의 대표(루트) 반환
  Union(x, y): x의 집합과 y의 집합을 합치기

🔴 [핵심 최적화 2가지]

  (1) 경로 압축 (Path Compression):
      Find 과정에서, 경로의 모든 노드를 직접 루트에 연결
      → 다음 Find가 O(1)에 가까워짐

      Before Find(4):     After Find(4):
           1                  1
          ╱                 ╱ | ╲
         2                2  3  4
        ╱
       3
      ╱
     4

  (2) 랭크 기반 합치기 (Union by Rank):
      작은 트리를 큰 트리 아래에 붙인다 → 높이 증가 최소화

  두 최적화를 합치면: 거의 O(1) (정확히는 O(α(n)), 역 아커만 함수)
  α(n)은 모든 실용적 n에 대해 ≤ 4 → 사실상 상수!

🔵 [CS 연결]
  크루스칼 MST 알고리즘: "이 간선이 사이클을 만드는가?" → Find로 확인
  네트워크 연결 요소 판별: "이 두 컴퓨터가 같은 네트워크인가?"
  이미지 세그멘테이션: 인접 픽셀 그룹화
  동적 그래프의 연결성 관리
```

## 12. 블룸 필터 — "아마도 있다, 확실히 없다"

```
🔴 [정의] 블룸 필터 (Bloom Filter):
  "원소가 집합에 있는가?"를 매우 빠르고 공간 효율적으로 답하는 확률적 자료구조

  답변: "확실히 없다" 또는 "아마 있다" (거짓 양성 가능, 거짓 음성 불가)

  동작:
    m비트 배열, k개의 해시 함수
    
    삽입: k개의 해시로 k개의 비트 위치를 계산, 모두 1로 설정
    검색: k개의 비트가 모두 1이면 "아마 있다", 하나라도 0이면 "확실히 없다"

왜 거짓 양성이 생기는가:
  다른 원소들이 설정한 비트가 우연히 모두 겹칠 수 있다.
  → 없는 원소인데도 모든 비트가 1일 수 있다.

왜 거짓 음성은 불가능한가:
  삽입할 때 비트를 1로 만들었으므로, 있는 원소의 비트는 반드시 모두 1.

🔵 [CS 연결]
  웹 브라우저: 악성 URL 검사 (Chrome의 Safe Browsing)
  DB: 디스크 접근 전에 "이 키가 이 파일에 있을 가능성이 있는가?" 빠른 체크
  캐시: "이 항목이 캐시에 있는가?" 빠른 검사
  비트코인: 트랜잭션 전파 필터링
  
  핵심 가치: 메모리를 극적으로 절약 (정확한 집합 저장 대비 ~10배 적은 공간)
  대가: 거짓 양성의 작은 확률
```

## 13. 자료구조 복잡도 총정리

```
┌──────────────┬────────┬────────┬────────┬────────┬──────────────┐
│ 자료구조      │ 접근    │ 검색    │ 삽입    │ 삭제    │ 특징          │
├──────────────┼────────┼────────┼────────┼────────┼──────────────┤
│ 배열          │ O(1)   │ O(n)   │ O(n)   │ O(n)   │ 캐시 효율 최고 │
│ 정렬 배열     │ O(1)   │O(logn) │ O(n)   │ O(n)   │ 이진 탐색 가능 │
│ 동적 배열     │ O(1)   │ O(n)   │ O(1)*  │ O(n)   │ *amortized   │
│ 연결 리스트   │ O(n)   │ O(n)   │ O(1)   │ O(1)   │ 포인터 오버헤드│
│ 해시 테이블   │  -     │ O(1)*  │ O(1)*  │ O(1)*  │ *평균, 정렬없음│
│ BST (균형)    │O(logn) │O(logn) │O(logn) │O(logn) │ 정렬 유지     │
│ 힙           │  -     │ O(n)   │O(logn) │O(logn) │ min/max O(1)  │
│ B+ 트리      │O(logn) │O(logn) │O(logn) │O(logn) │ 디스크 최적화  │
│ 트라이        │  -     │ O(m)   │ O(m)   │ O(m)   │ m=키 길이     │
│ 유니온파인드   │  -     │O(α(n)) │  -     │  -     │ ≈ O(1)       │
│ 블룸 필터     │  -     │ O(k)   │ O(k)   │  -     │ 확률적, 삭제불가│
└──────────────┴────────┴────────┴────────┴────────┴──────────────┘
```

## 14. 자료구조 선택 가이드

```
"나는 무엇을 자주 하는가?"에 따라 선택한다:

  인덱스로 빠르게 접근?        → 배열
  맨 뒤에 추가/삭제?           → 동적 배열 (스택도 가능)
  맨 앞에 추가/삭제?           → 연결 리스트 또는 덱
  키로 빠르게 검색?            → 해시 테이블
  정렬된 상태로 유지하면서 검색? → 균형 BST (TreeMap)
  최소/최대를 빠르게?           → 힙
  범위 검색 + 디스크 I/O 최소? → B+ 트리
  접두사 검색?                 → 트라이
  "같은 그룹인가?" 반복 질문?   → 유니온-파인드
  "이것이 집합에 있는가?" 대략? → 블룸 필터
  LIFO 순서?                   → 스택
  FIFO 순서?                   → 큐
  우선순위 순서?                → 힙 (우선순위 큐)
```

## 16. 정리 — 자료구조를 관통하는 원리

```
[원리 1] 트레이드오프: 만능은 없다. 한 연산을 빠르게 하면 다른 것이 느려진다.
  → 문제의 연산 패턴을 분석한 후 자료구조를 선택한다.

[원리 2] 연속 메모리 = O(1) 접근 + 캐시 효율.
  → 배열이 빠른 이유. 주소 산술.

[원리 3] 포인터 = 삽입/삭제 유연성.
  → 연결 리스트가 빠른 이유. 이동 불필요.

[원리 4] 접근 제한 = 행동 보장.
  → 스택(LIFO), 큐(FIFO)의 존재 이유. 제한이 곧 유용성.

[원리 5] 해싱 = 키 → 주소 직접 변환.
  → O(1) 검색의 마법. 대가는 충돌 관리와 정렬 불가.

[원리 6] "반씩 줄이기" = O(log n).
  → 이진 탐색, BST, 힙이 빠른 공통 이유.

[원리 7] 분기 수 증가 = 높이 감소 = 디스크 I/O 감소.
  → B-트리가 존재하는 이유. 이진이 아닌 다진 트리.

[원리 8] 확률적 보장으로 공간/시간 절약.
  → 블룸 필터. 완벽한 정확도를 포기하면 극적인 효율.

외워야 할 것:
  🔴 각 자료구조의 핵심 연산 복잡도 (§13 표)
  🔴 해시 테이블의 충돌 해결 전략 (체이닝, 개방 주소법)
  🔴 힙의 부모/자식 인덱스 공식
  🔴 BST 성질 (왼쪽 < 루트 < 오른쪽)
  🔴 B+ 트리의 핵심 특성 (데이터는 리프, 리프 연결)
  🔴 유니온-파인드의 두 최적화 (경로 압축 + 랭크 합치기)

유도할 수 있는 것:
  🟢 동적 배열의 amortized O(1) (총 비용 분석)
  🟢 힙 연산이 O(log n)인 이유 (완전 이진 트리 높이)
  🟢 heapify가 O(n)인 이유 (기하급수 합)
  🟢 AVL 트리 높이 ≤ 1.44 log n (피보나치 연결)
  🟢 유니온-파인드가 거의 O(1)인 이유 (두 최적화 결합)
```
