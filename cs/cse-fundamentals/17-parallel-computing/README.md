## 1. 출발점: 왜 병렬이 필요한가

### 1.1 무어의 법칙의 종말

```
🔴 [자연의 제약]

2000년대 이전: 클록 속도가 매 2년마다 2배 → "가만히 있어도 코드가 빨라졌다"
2005년 이후: 클록 속도가 ~4GHz에서 정체 → 물리적 한계 (발열, 전력)

  클록을 2배로 올리면 → 전력 소비 ≈ 8배 (전력 ∝ 주파수³)
  → 더 이상 주파수를 올려서 빠르게 할 수 없다!

해결: 코어를 여러 개 넣자 (멀티코어)
  → 그러나 프로그램이 여러 코어를 활용하려면 → 병렬 프로그래밍이 필요하다
  → "공짜 점심"은 끝났다. 성능을 얻으려면 프로그래머가 노력해야 한다.
```

### 1.2 암달의 법칙 — 병렬화의 근본 한계 (Ch.11 복습 + 심화)

```
🔴 Speedup = 1 / ((1-p) + p/n)

  p = 병렬화 가능 비율, n = 프로세서 수
  n → ∞이면: Speedup_max = 1/(1-p)

  p = 0.95 → 최대 20배. p = 0.99 → 최대 100배.
  1%의 직렬 부분이 100배의 한계를 만든다!

🔴 구스타프슨의 법칙 — 다른 관점:
  "프로세서가 많아지면, 더 큰 문제를 같은 시간에 풀 수 있다"
  
  Speedup = n - (1-p)(n-1) ≈ n·p + (1-p)
  
  암달: "고정된 문제 크기에서 몇 배 빨라지나" → 비관적
  구스타프슨: "같은 시간에 몇 배 큰 문제를 풀 수 있나" → 낙관적
  
  현실은 둘 다 맞다. 관점의 차이.
```

## 2. 공유 메모리 모델 — "같은 메모리를 나눠 쓰기"

### 2.1 원리와 문제

```
🔴 [모델] 여러 스레드가 같은 주소 공간의 메모리를 읽고 쓴다.

  장점: 통신이 빠르다 (메모리 접근 = 나노초)
  문제: 동기화가 필수! (Ch.12의 경쟁 상태, 데드락 재등장)

  스레드 1: x = x + 1
  스레드 2: x = x + 1
  → x가 1만 증가할 수 있다! (읽기-수정-쓰기가 원자적이지 않으므로)
```

### 2.2 동기화 도구 (Ch.12 복습 + 확장)

```
🔴 Lock (뮤텍스): 임계 구역 보호. 간단하지만 데드락 위험.

🔴 Lock-free 자료구조:
  잠금 없이 원자적 연산(CAS)으로 동시성을 보장.
  
  CAS(Compare-And-Swap):
    "현재 값이 expected이면 new_value로 교체. 아니면 실패."
    하드웨어가 원자적으로 보장!
    
    의사코드:
    do {
        old = read(x);
        new = old + 1;
    } while (!CAS(&x, old, new));  // 실패하면 재시도
  
  왜 Lock-free가 중요한가:
    Lock: 한 스레드가 잠금을 잡고 죽으면 → 전체가 멈춤
    Lock-free: 어떤 스레드가 멈춰도 나머지는 진행 가능
    
    → 고성능 시스템, 실시간 시스템에서 중요

🔴 Barrier (배리어):
  모든 스레드가 특정 지점에 도달할 때까지 대기.
  "모두 준비되면 함께 다음 단계로"
  → 행렬 곱셈의 단계별 동기화 등에 사용
```

### 2.3 병렬 패턴 — 문제를 어떻게 병렬화하는가

```
🔴 주요 병렬 패턴:

  (1) 데이터 병렬 (Data Parallelism):
    같은 연산을 다른 데이터에 동시 적용.
    for i in range(n): a[i] = b[i] + c[i]  → n개를 동시에!
    → SIMD, GPU의 핵심 모델
    → 벡터/행렬 연산, 이미지 처리에 이상적

  (2) 태스크 병렬 (Task Parallelism):
    서로 다른 작업을 동시에 실행.
    스레드 1: 데이터 로딩
    스레드 2: 계산
    스레드 3: 결과 저장
    → 파이프라인, 비동기 처리

  (3) 분할 정복 (Divide and Conquer):
    문제를 나누고 각 부분을 병렬로 풀고 합친다.
    → 병렬 머지 정렬, 병렬 퀵 정렬

  (4) 생산자-소비자 (Producer-Consumer):
    생산자가 데이터를 큐에 넣고, 소비자가 꺼내 처리.
    → 웹 서버의 요청 큐, 로그 처리 파이프라인
```

## 3. 메시지 전달 모델 — "각자의 메모리, 메시지로 소통"

```
🔴 [모델] 각 프로세스가 독립된 메모리를 가지고, 메시지를 주고받아 통신.

  MPI (Message Passing Interface): 분산 메모리 시스템의 표준 API.
    Send(data, destination)
    Receive(data, source)

  공유 메모리 vs 메시지 전달:
    공유 메모리: 빠르지만 동기화 복잡. 단일 머신 내.
    메시지 전달: 동기화가 명시적(메시지). 여러 머신으로 확장 가능.

  왜 메시지 전달이 대규모에 유리한가:
    공유 메모리: 메모리 일관성 유지 비용이 코어 수에 따라 급증
    메시지 전달: 각 노드가 독립 → 수천~수만 노드까지 확장 가능
    → 슈퍼컴퓨터, 클라우드 클러스터의 기반

  🔵 Erlang/Elixir의 액터 모델:
    각 액터가 독립된 상태 + 메시지 큐를 가짐.
    "공유 상태 없음" → 경쟁 상태 원천 차단!
    → WhatsApp이 Erlang으로 수백만 동시 접속을 처리한 이유.
```

## 4. GPU 컴퓨팅 — "수천 코어의 힘"

```
🔴 GPU의 핵심: 대규모 데이터 병렬 처리

  CPU: 복잡한 제어 흐름, 소수의 강력한 코어 (4~64)
  GPU: 단순한 연산, 수천 개의 작은 코어 (수천~수만)

  CUDA 프로그래밍 모델:
    커널(kernel): GPU에서 실행되는 함수
    스레드 블록: 스레드의 그룹 (공유 메모리 가능)
    그리드: 블록의 그룹
    
    개념적 흐름:
    (1) CPU에서 데이터를 GPU 메모리로 복사
    (2) GPU에서 수천 스레드가 동시에 커널 실행
    (3) 결과를 GPU에서 CPU로 복사

  왜 모든 것에 GPU를 쓰지 않는가:
    (1) 분기(if/else)가 많은 코드: GPU 스레드들이 같은 명령어를 실행해야 효율적.
        분기가 다르면 → 일부 스레드가 대기 → 효율 급락 (warp divergence)
    (2) 순차적 의존성: 이전 결과에 다음 계산이 의존하면 → 병렬화 불가
    (3) 데이터 전송 비용: CPU↔GPU 데이터 복사가 병목이 될 수 있음

🔵 딥러닝에서 GPU가 필수인 이유:
  행렬 곱 Y = WX: 각 출력 원소 = 독립적인 내적
  → 수천 개의 내적을 수천 코어가 동시에 계산
  → CPU 대비 10~100배 빠른 학습
```

## 5. MapReduce와 Spark — 빅데이터 처리

### 5.1 MapReduce — 왜 이 구조인가

```
🔴 [모델] Google (2004):
  대규모 데이터를 "Map 단계 → Shuffle → Reduce 단계"로 처리.

  Map:    각 데이터에 독립적인 함수 적용 → (key, value) 쌍 생성
  Shuffle: 같은 key를 가진 값들을 모음 (프레임워크가 자동)
  Reduce: 각 key에 대해 값들을 집계

  예시: 단어 빈도 수 세기
    입력: ["hello world", "hello mapreduce"]
    
    Map:    "hello world" → [("hello",1), ("world",1)]
            "hello mapreduce" → [("hello",1), ("mapreduce",1)]
    
    Shuffle: "hello" → [1, 1],  "world" → [1],  "mapreduce" → [1]
    
    Reduce:  "hello" → 2,  "world" → 1,  "mapreduce" → 1

왜 이 구조가 강력한가:
  (1) Map은 완전 병렬! 각 데이터 조각을 독립적으로 처리 → 수천 노드 활용
  (2) 프로그래머는 Map과 Reduce만 작성. 분산, 장애 복구는 프레임워크가 처리!
  (3) 함수형 프로그래밍의 map과 reduce에서 영감

🔴 Spark — MapReduce의 한계 극복:
  MapReduce의 문제: 매 단계마다 디스크에 쓰고 읽음 → 반복 계산이 느림
  Spark: 중간 결과를 메모리에 유지 (RDD, DataFrame)
  → 머신러닝 같은 반복 알고리즘에서 10~100배 빠름!
```

## 6. 분산 시스템의 합의 — "모두가 동의하기"

### 6.1 합의 문제 — 왜 어려운가

```
🔴 [문제] 여러 노드가 하나의 값에 동의해야 한다.
  그런데 네트워크는 지연되고, 패킷은 유실되고, 노드는 죽을 수 있다!

  왜 합의가 필요한가:
    "이 트랜잭션이 커밋되었는가?" — 모든 복제본이 동의해야!
    "누가 리더인가?" — 분산 시스템에서 하나의 리더를 선출해야!
    
  🔴 FLP 불가능성 정리 (1985):
    비동기 시스템에서 하나의 노드라도 장애 가능하면,
    결정적 합의 알고리즘은 존재하지 않는다!
    
    → 현실의 합의 알고리즘은 타임아웃 같은 현실적 가정을 추가하여 우회.
```

### 6.2 Paxos와 Raft — 어떻게 합의하는가

```
🔴 Paxos (Lamport, 1990):
  가장 유명한 합의 알고리즘. 정확하지만 이해하기 매우 어렵다.
  
  핵심: Proposer가 값을 제안 → Acceptor들이 과반수 합의 → 결정
  
  "이해하기 어렵다"는 문제를 해결한 것이:

🔴 Raft (2014):
  Paxos와 동등한 안전성, 이해 가능하도록 설계.
  
  세 가지 역할: Leader, Follower, Candidate
  
  리더 선출:
    리더가 죽으면 → 타임아웃 → Candidate가 투표 요청 → 과반수 획득 → 새 리더!
  
  로그 복제:
    리더가 명령을 로그에 추가 → Follower에 전파 → 과반수 확인 → 커밋!
  
  왜 과반수인가:
    과반수끼리는 반드시 겹침 → 두 그룹이 다른 결정을 내릴 수 없다!
    n개 노드 중 과반수 = ⌊n/2⌋ + 1
    5개 노드이면 3개가 동의해야 → 최대 2개 노드 장애 허용

🔵 [CS 연결]
  etcd (Kubernetes의 저장소): Raft
  ZooKeeper: ZAB (Paxos 변형)
  Google Spanner: Paxos
  → 모든 현대 분산 시스템의 핵심에 합의 알고리즘이 있다
```

### 6.3 일관성 해싱 — 노드 추가/제거의 비용 최소화

```
🔴 [문제] n개 노드에 데이터를 분산할 때, 노드가 추가/제거되면?
  단순 해싱: hash(key) % n → n이 바뀌면 거의 모든 데이터가 재배치!
  
  일관성 해싱 (Consistent Hashing):
    노드와 키를 같은 해시 링(ring) 위에 배치.
    각 키는 시계 방향으로 가장 가까운 노드에 저장.
    
    노드 추가/제거 시: 영향 받는 키 = 전체의 약 1/n만!
    
    왜: 링 위에서 한 노드만 이동하면, 그 노드와 이전 노드 사이의 키만 재배치.
    나머지 키는 영향 없음!

🔵 Amazon DynamoDB, Cassandra, CDN의 핵심 기술.
```

## 8. 정리

```
[원리 1] 무어의 법칙 종말 → 성능 = 병렬화. "공짜 점심"은 끝났다.
[원리 2] 암달의 법칙: 직렬 부분이 병렬 속도향상의 상한을 결정.
[원리 3] 공유 메모리: 빠르지만 동기화 복잡. Lock → Lock-free → Wait-free.
[원리 4] 메시지 전달: 확장성 좋지만 통신 비용. 대규모 분산에 적합.
[원리 5] GPU: 대규모 데이터 병렬. 분기 적고 독립 연산이 많은 문제에 최적.
[원리 6] MapReduce: Map(병렬 변환) + Reduce(집계). 프로그래머는 로직만.
[원리 7] 합의: 분산 시스템의 핵심 난제. 과반수 원리가 핵심.

외워야 할 것:
  🔴 암달의 법칙, 구스타프슨의 법칙 공식
  🔴 공유 메모리 vs 메시지 전달의 트레이드오프
  🔴 CAS 연산의 원리
  🔴 MapReduce의 세 단계 (Map, Shuffle, Reduce)
  🔴 Raft의 핵심 (리더 선출 + 로그 복제 + 과반수)
  🔴 일관성 해싱의 원리와 장점
```
