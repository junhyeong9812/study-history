## 1. 출발점: 왜 프로그래밍 언어를 "이론적으로" 공부하는가

### 1.1 PLT를 배우는 이유

```
"하나의 언어만 아는 프로그래머는 진정한 프로그래머가 아니다."

PLT를 공부하면:
  (1) 새 언어를 빠르게 습득하는 "메타 능력"이 생긴다
      → 언어마다 다른 것은 문법(표면), 같은 것은 원리(깊이)
      → 원리를 알면 문법은 금방 익힌다
  
  (2) 언어의 설계 결정 이유를 이해한다
      "왜 Python은 동적 타입이고 Java는 정적 타입인가?"
      "왜 Rust는 GC가 없는데도 안전한가?"
      → 각 선택에는 트레이드오프가 있다
  
  (3) 컴파일러/인터프리터의 동작을 이해한다
      → 코드가 "실제로 어떻게 실행되는가"를 아는 것

  (4) 더 나은 코드를 작성한다
      → 타입 시스템을 이해하면 버그를 예방하는 코드를 쓸 수 있다
      → 클로저, 고차 함수를 이해하면 더 추상적이고 재사용 가능한 코드를 쓸 수 있다
```

## 2. 프로그래밍 패러다임 — "사고의 틀"

### 2.1 왜 여러 패러다임이 존재하는가

```
🔴 [핵심] 같은 문제를 바라보는 "관점"이 다르다.

  명령형: "어떻게(how) 하는지 단계별로 지시한다"
  선언형: "무엇을(what) 원하는지 기술한다"
  
  이 두 가지 근본 관점에서 여러 패러다임이 파생된다.
```

### 2.2 명령형 (Imperative) — "단계별 지시"

```
🔴 [정의] 상태(변수)를 변경하는 문장(statement)의 연속.
  프로그래머가 "어떻게" 계산할지를 구체적으로 지시.

  x = 0
  for i in range(10):
      x = x + i       ← 상태(x)를 반복적으로 변경

  하위 분류:
    절차적 (Procedural): 함수/프로시저로 구조화. C, Pascal.
    객체지향 (OOP): 데이터+행동을 객체로 묶음. Java, C++, Python.

  OOP의 4 원칙:
    캡슐화: 내부 구현 숨기기 → 변경 시 외부 영향 최소화
    상속: 기존 클래스를 확장 → 코드 재사용
    다형성: 같은 인터페이스, 다른 구현 → 유연한 설계
    추상화: 복잡한 현실을 핵심만 모델링

  왜 OOP가 지배적이었나:
    현실 세계를 "객체"로 모델링하는 것이 직관적.
    대규모 소프트웨어의 모듈화와 유지보수에 유리.

  OOP의 한계:
    상태 변이(mutation) → 동시성 문제 (Ch.12 경쟁 상태!)
    상속 계층이 깊어지면 → 복잡도 폭발 ("갓 클래스")
    → 함수형 프로그래밍이 대안으로 부상
```

### 2.3 함수형 (Functional) — "값을 변환"

```
🔴 [정의] 순수 함수의 합성으로 계산을 표현.
  상태 변이 없음(immutability). 같은 입력 → 항상 같은 출력.

  # 명령형: "어떻게" — 상태를 변경하며 루프
  result = 0
  for x in [1,2,3,4,5]:
      result += x * x

  # 함수형: "무엇을" — 변환을 합성
  result = sum(map(lambda x: x*x, [1,2,3,4,5]))

핵심 개념:
  순수 함수: 부수 효과(side effect) 없음. 외부 상태를 읽지도 쓰지도 않음.
  불변성: 데이터를 변경하지 않고 새 데이터를 반환.
  일급 함수: 함수를 변수에 담고, 인수로 전달하고, 반환값으로 사용.
  고차 함수: 함수를 인수로 받거나 반환하는 함수. (map, filter, reduce)

왜 함수형이 다시 주목받는가:
  (1) 불변성 → 동시성 문제가 원천 차단! (공유 상태가 없으니 경쟁 상태 불가)
  (2) 순수 함수 → 테스트와 추론이 쉽다 (외부 의존 없음)
  (3) 합성 가능 → 작은 함수를 조합하여 복잡한 로직 구성
  (4) 지연 평가 → 무한 데이터 구조 가능 (필요할 때만 계산)

  Haskell, Erlang, Clojure, F# — 순수 함수형
  Scala, Kotlin, Swift, Rust — 다중 패러다임 (함수형 포함)
  JavaScript, Python — 함수형 기능을 점차 채용
```

### 2.4 논리형과 선언형

```
논리형 (Logic): 논리적 관계를 선언하고, 추론 엔진이 답을 찾는다.
  Prolog: parent(tom, bob). parent(bob, ann).
          grandparent(X, Z) :- parent(X, Y), parent(Y, Z).
          ?- grandparent(tom, ann).  → true
  
  🔵 인공지능 초기, 전문가 시스템, 자연어 처리에 사용됨.

선언형 (Declarative): "무엇을" 원하는지만 기술.
  SQL: SELECT name FROM students WHERE gpa > 3.5
  HTML/CSS: 구조와 스타일을 기술 (렌더링은 브라우저가)
  정규식: 패턴을 기술 (매칭은 엔진이)
  
  🔵 선언형의 장점: 사용자는 "what"에 집중, "how"는 시스템이 최적화.
     Ch.15 SQL에서 이미 다뤘다.
```

## 3. 구문론 — "프로그램의 형태"

### 3.1 BNF와 문맥 자유 문법 — 왜 이것으로 문법을 정의하는가

```
🔴 [정의] BNF (Backus-Naur Form):
  프로그래밍 언어의 문법을 형식적으로 정의하는 표기법.

  <expr>   ::= <term> | <expr> "+" <term>
  <term>   ::= <factor> | <term> "*" <factor>
  <factor> ::= "(" <expr> ")" | <number>
  <number> ::= "0" | "1" | ... | "9"

  읽는 법:
    <expr>는 <term>이거나, <expr> + <term>이다.
    ::= 는 "...로 정의된다"
    | 는 "또는"
    <...>는 비단말 기호 (더 분해될 수 있는 것)
    "..."는 단말 기호 (실제 문자)

왜 BNF/CFG를 쓰는가:
  (1) 모호하지 않게 문법을 정의할 수 있다 → 컴파일러가 이해 가능
  (2) 연산자 우선순위를 자연스럽게 표현
      위 문법에서: *가 +보다 먼저 계산됨 (트리 아래쪽에 있으므로)
  (3) Ch.04의 오토마타/형식 언어 이론에 직접 대응
      CFG → 푸시다운 오토마타 → 파서

연산자 우선순위가 문법에 인코딩되는 방식:
  3 + 4 * 5의 파스 트리:

        <expr>
       ╱  │  ╲
   <expr> "+" <term>
     │       ╱  │  ╲
   <term> <term>"*"<factor>
     │      │       │
  <factor><factor>  5
     │      │
     3      4

  * 가 트리 아래에 있으므로 먼저 계산됨!
  → 우선순위를 문법 규칙의 계층으로 표현.
```

### 3.2 어휘 분석과 구문 분석 — 컴파일러의 입구

```
🔴 [과정]

  소스 코드 문자열: "x = 3 + 4 * 5;"

  (1) 어휘 분석 (Lexing/Tokenizing):
      문자 스트림 → 토큰 스트림
      "x" → ID("x"), "=" → ASSIGN, "3" → NUM(3), "+" → PLUS, ...
      
      도구: 정규 표현식 → DFA (Ch.04 오토마타!)
      
      왜 정규식으로 충분한가:
        토큰의 구조는 단순하다 (식별자 = [a-z][a-z0-9]*, 숫자 = [0-9]+)
        → 정규 언어로 표현 가능 → DFA로 인식

  (2) 구문 분석 (Parsing):
      토큰 스트림 → AST (추상 구문 트리)
      
      하향식 (Top-Down): LL 파서, 재귀 하강
        문법의 시작 기호에서 출발, 입력과 매칭하며 확장
      
      상향식 (Bottom-Up): LR, LALR 파서
        입력에서 출발, 문법 규칙을 역적용하여 시작 기호로 축약
      
      왜 두 방식이 있는가:
        하향식: 직관적, 수동 구현 쉬움 → 많은 컴파일러가 재귀 하강 사용
        상향식: 더 넓은 문법 인식 가능 → 복잡한 문법에 적합 → yacc/bison 도구

  파스 트리 vs AST:
    파스 트리: 문법 규칙의 모든 단계를 포함 (장황)
    AST: 의미에 필요한 구조만 남긴 간결한 트리
    
    "3 + 4 * 5"의 AST:
        [+]
       ╱   ╲
     [3]   [*]
          ╱   ╲
        [4]   [5]
```

## 4. 의미론 — "프로그램이 무엇을 의미하는가"

### 4.1 왜 의미론이 필요한가

```
구문은 "형태"를 정의한다. 의미론은 "행동"을 정의한다.

  구문적으로 올바르지만 의미가 다른 예:
    "3 / 0" → 구문 OK, 의미 = 오류!
    "int x = 'hello'" → 구문 OK(일부 언어), 의미 = 타입 오류!

```

### 4.2 조작적 의미론 — "실행해보면 안다"

```
🔴 [정의] 프로그램의 의미 = "추상 기계에서 실행했을 때의 행동"

  규칙 형태: <문장, 상태> → <상태'>
  "이 문장을 이 상태에서 실행하면 이 새 상태가 된다"

  예: <x = 3, {}> → {x: 3}
      <x = x + 1, {x: 3}> → {x: 4}

왜 유용한가:
  인터프리터를 정의하는 것과 같다.
  "이 언어의 인터프리터를 작성하라" = 조작적 의미론을 구현하라.
  가장 직관적이고 구현에 가까운 의미론.

🔵 [CS 연결]
  언어 명세(specification)에서 가장 흔히 사용.
  Python, JavaScript의 공식 명세가 조작적 스타일.
```

### 4.3 표시적 의미론 — "수학적 함수로 대응"

```
🔴 [정의] 프로그램의 의미 = 수학적 함수
  각 프로그램 구성 요소를 수학적 대상(함수, 집합 등)에 대응시킨다.

  ⟦x = 3⟧ = λσ. σ[x ↦ 3]
  "x = 3의 의미는, 상태 σ를 받아 x를 3으로 바꾼 새 상태를 반환하는 함수"

  ⟦...⟧ = "의미 함수" (double bracket으로 표기, "시맨틱 브래킷")

왜 유용한가:
  수학적 성질(동치, 정당성)을 증명할 수 있다.
  프로그램 최적화의 정당성을 엄밀하게 보장.
```

### 4.4 공리적 의미론 — "참이 되는 조건"

```
🔴 [정의] 프로그램의 의미 = 사전/사후 조건의 관계 (Hoare Logic)

  {P} S {Q}
  "P가 참인 상태에서 S를 실행하면, Q가 참이 된다"
  
  {P}: 사전 조건 (precondition)
  S:   프로그램 문장
  {Q}: 사후 조건 (postcondition)

  예: {x = 3} x = x + 1 {x = 4}
      {n ≥ 0} factorial(n) {result = n!}

왜 유용한가:
  프로그램의 정당성(correctness)을 형식적으로 증명할 수 있다!
  "이 프로그램이 명세를 만족한다"를 수학적으로 보장.
  
  🔵 항공기, 의료기기 등 안전 필수(safety-critical) 시스템에서 사용.
  → 형식 검증(formal verification)의 기반.
```

## 5. 변수, 바인딩, 스코프 — "이름이 무엇을 가리키는가"

### 5.1 바인딩 — 이름과 속성의 연결

```
🔴 [정의] 바인딩(binding): 이름에 속성(타입, 값, 주소 등)을 연결하는 것.

  바인딩 시점이 핵심:
    설계 시: 연산자의 의미 (+ = 덧셈)
    컴파일 시: 변수의 타입 (int x → x는 정수)
    링크 시: 외부 함수의 주소
    실행 시: 변수의 값 (x = 42)

  왜 시점이 중요한가:
    빠른 바인딩 (정적, 컴파일 시): 효율적, 최적화 가능, 유연성 낮음
    늦은 바인딩 (동적, 실행 시): 유연, 최적화 어려움, 오류 늦게 발견
    
    정적 타입 (Java, C): 타입이 컴파일 시 바인딩 → 빠르고 안전
    동적 타입 (Python, JS): 타입이 실행 시 바인딩 → 유연하지만 런타임 오류
```

### 5.2 스코프 — 변수가 보이는 범위

```
🔴 [정의] 스코프(scope): 변수 이름이 유효한 코드 영역.

  정적 스코프 (Lexical Scope):
    코드의 구조(텍스트 위치)로 결정. 대부분의 현대 언어.
    
    x = 10
    def f():
        print(x)    ← x는 정의된 위치를 기준으로 찾는다 → 10
    def g():
        x = 20
        f()         ← f 안의 x는 여전히 바깥의 x (= 10)

  동적 스코프 (Dynamic Scope):
    호출 순서로 결정. Bash, 일부 Lisp.
    
    같은 코드에서 동적 스코프이면:
    g()가 f()를 호출 → f 안의 x는 g의 x (= 20)를 본다
    
  왜 정적 스코프가 표준인가:
    코드를 읽는 것만으로 변수가 뭘 가리키는지 알 수 있다 (예측 가능).
    동적 스코프는 호출 맥락에 따라 달라짐 → 추론이 어렵고 버그 유발.
```

### 5.3 클로저 — 왜 이것이 중요한가

```
🔴 [정의] 클로저(closure): 함수 + 그 함수가 정의된 환경(자유 변수)을 함께 캡처한 것.

  def make_counter():
      count = 0              ← 자유 변수
      def increment():
          nonlocal count
          count += 1         ← 클로저: increment는 count를 "기억"한다
          return count
      return increment
  
  counter = make_counter()
  counter()  → 1
  counter()  → 2
  counter()  → 3

  make_counter()는 이미 리턴했지만, count는 클로저 안에 살아있다!

왜 이것이 중요한가:
  (1) 상태를 캡슐화: 전역 변수 없이도 상태를 유지
  (2) 함수 팩토리: 설정에 따라 다른 함수를 생성
  (3) 콜백/이벤트 핸들러: 정의 시점의 맥락을 기억
  (4) 함수형 프로그래밍의 기반: 부분 적용(partial application), 커링

  🔵 JavaScript의 이벤트 핸들러, React의 훅, Python의 데코레이터
     모두 클로저에 의존한다.
```

## 6. 타입 시스템 — "값의 분류와 안전성"

### 6.1 타입이란 — 왜 필요한가

```
🔴 [정의] 타입(type): 값의 집합 + 그 값에 적용 가능한 연산의 정의.
  int = {..., -2, -1, 0, 1, 2, ...} + {+, -, *, /, %, ...}
  string = {"", "a", "ab", ...} + {concat, length, substring, ...}

왜 타입이 필요한가:
  "hello" + 3은 무엇인가?
  - 타입이 없으면: 메모리의 비트 패턴을 그냥 더함 → 의미 없는 결과 (또는 크래시)
  - 타입이 있으면: "string + int는 허용되지 않음" → 오류를 미리 방지!

  타입 = "이 값에 이 연산을 적용해도 되는가?"를 판단하는 규칙
  → 타입 검사 = "프로그램이 의미 있는 연산만 하는지" 확인
```

### 6.2 정적 vs 동적 타입 — 왜 두 진영이 있는가

```
🔴 정적 타입 (Static Typing):
  컴파일 시 타입을 검사. 실행 전에 타입 오류를 발견.
  Java, C, C++, Rust, Go, Haskell, TypeScript

  장점: 실행 전 오류 발견, 최적화 가능 (타입을 알면 메모리 레이아웃 결정)
  단점: 타입 선언이 장황할 수 있음, 유연성 낮음

🔴 동적 타입 (Dynamic Typing):
  실행 시 타입을 검사. 변수에 아무 타입이나 담을 수 있음.
  Python, JavaScript, Ruby, Lisp

  장점: 코드가 짧고 유연, 프로토타이핑이 빠름
  단점: 실행해봐야 오류 발견, 최적화 어려움

트레이드오프의 본질:
  "빨리 쓰고 나중에 문제를 찾을 것인가" vs "천천히 쓰되 미리 문제를 잡을 것인가"
  
  큰 프로젝트: 정적 타입이 유리 (협업 시 인터페이스 명확, 리팩토링 안전)
  작은 스크립트: 동적 타입이 유리 (빠른 개발)
  
  중간 지대:
    TypeScript: JavaScript + 정적 타입 (점진적 타입 시스템)
    Python 타입 힌트: 선택적 정적 분석 (mypy)
```

### 6.3 타입 추론 — 왜 선언 없이도 타입을 알 수 있는가

```
🔴 [정의] 타입 추론(type inference):
  프로그래머가 타입을 명시하지 않아도 컴파일러가 자동으로 결정.

  Haskell: add x y = x + y → 컴파일러가 Num a => a -> a -> a로 추론
  Rust:    let x = 42;    → 컴파일러가 i32로 추론
  C++:     auto x = 42;   → 컴파일러가 int로 추론

왜 가능한가:
  사용 맥락에서 타입을 역추론한다.
  x + y에서 +가 숫자에만 정의 → x, y는 숫자 타입이어야 함
  
  Hindley-Milner 타입 추론:
    타입 방정식을 세우고 → 통합(unification)으로 풀기
    → 가장 일반적인 타입(principal type)을 자동으로 결정
    → Haskell, ML, OCaml의 핵심 기능

왜 좋은가:
  정적 타입의 안전성 + 동적 타입의 간결함을 동시에!
  "타입을 안 써도 되는 정적 타입 언어" → 최고의 조합
```

### 6.4 다형성 — 하나의 코드, 여러 타입

```
🔴 세 종류의 다형성:

(1) 매개변수 다형성 (Parametric / Generics):
  타입을 "매개변수"로 받는다.
  
  Java: List<T> → List<Integer>, List<String> → 같은 코드, 다른 타입
  Haskell: length :: [a] -> Int → 어떤 타입의 리스트든 길이 계산
  
  왜 필요한가: "int 리스트의 길이"와 "string 리스트의 길이"를 따로 구현하는 것은 낭비.
  타입만 다르고 로직이 같으면 → 제네릭으로 한 번만 작성.

(2) 서브타입 다형성 (Subtype / 상속):
  자식 타입이 부모 타입 자리에 올 수 있다.
  
  Animal a = new Dog();  → Dog은 Animal의 서브타입
  a.speak();             → Dog의 speak()이 호출됨 (동적 디스패치)
  
  왜 필요한가: "어떤 동물이든 speak() 할 수 있다"를 표현.
  구체적 타입에 무관하게 코드를 작성 → 확장에 유연.

(3) 임시 다형성 (Ad-hoc / 오버로딩):
  같은 이름의 함수가 타입에 따라 다른 구현.
  
  Java: + 는 int끼리 덧셈, String끼리 연결
  Haskell: 타입 클래스 (class Eq a where (==) :: a -> a -> Bool)
  
  왜 필요한가: 같은 "개념"(같음, 비교, 출력)이 타입마다 다르게 구현될 때.
```

## 7. 메모리 관리 — "누가 메모리를 정리하는가"

### 7.1 세 가지 전략 — 각각의 트레이드오프

```
🔴 (1) 수동 관리 (Manual): C, C++
  프로그래머가 malloc/free, new/delete로 직접 관리.
  
  장점: 최대 제어, 예측 가능한 성능
  단점: 실수 → 메모리 누수, 댕글링 포인터, 이중 해제, 버퍼 오버플로
  → 보안 취약점의 주요 원인! (Ch.14)

🔴 (2) 가비지 컬렉션 (GC): Java, Python, Go, JavaScript
  런타임이 "더 이상 사용되지 않는 객체"를 자동으로 정리.
  
  장점: 프로그래머가 해제를 신경 쓰지 않아도 됨, 안전
  단점: GC가 실행될 때 프로그램이 멈출 수 있음 (stop-the-world pause)
  
  주요 GC 알고리즘:
    참조 카운팅 (Reference Counting):
      각 객체에 "참조 수"를 유지. 0이 되면 해제.
      문제: 순환 참조! A→B→A → 둘 다 참조 수 1 → 영원히 해제 안 됨!
      → Python: 참조 카운팅 + 순환 탐지기를 함께 사용
    
    Mark-and-Sweep:
      루트(전역변수, 스택)에서 출발하여 도달 가능한 객체를 "마킹".
      마킹 안 된 것은 "쓰레기" → 해제.
      문제: 전체 힙을 순회해야 → 느릴 수 있음
    
    세대별 GC (Generational):
      🔴 관찰: "대부분의 객체는 금방 죽는다" (약한 세대 가설)
      Young 세대: 자주 수집, 빠름 (대부분 여기서 죽음)
      Old 세대: 가끔 수집, 느림 (오래 살아남은 것)
      → Young이 작으므로 GC가 빠르다!
      → Java G1GC, ZGC, Go의 GC가 이 원리 기반.

🔴 (3) 소유권 시스템 (Ownership): Rust
  GC 없이 컴파일 시점에 메모리 안전성을 보장!
  
  규칙:
    각 값은 정확히 하나의 소유자(owner)를 가진다.
    소유자가 스코프를 벗어나면 값이 자동 해제.
    값을 빌려줄(borrow) 수 있지만, 규칙에 따라:
      &T (불변 참조): 여러 개 가능
      &mut T (가변 참조): 하나만 가능 (동시 불변 참조와 공존 불가)
  
  왜 이것이 혁명적인가:
    수동 관리의 제어 + GC의 안전성을 모두 달성.
    GC의 성능 오버헤드(pause) 없음.
    데이터 레이스를 컴파일 시점에 방지!
    대가: 학습 곡선이 가파르다 (컴파일러와 "싸워야" 함).
```

## 8. 제어 흐름 — "프로그램의 실행 순서"

### 8.1 재귀 vs 반복 — 같은 것의 두 표현

```
🟢 [유도 가능] 모든 재귀는 반복으로, 모든 반복은 재귀로 변환 가능.
  (스택을 명시적으로 사용하면 재귀 = 반복)

  그런데 왜 둘 다 존재하는가:
    반복: 상태 변이 중심. 성능 예측 쉬움. 명령형에 자연스러움.
    재귀: 수학적 정의에 가까움. 분할 정복에 자연스러움. 함수형에 자연스러움.

  꼬리 재귀 최적화 (TCO):
    재귀 호출이 함수의 마지막 연산이면 → 스택 프레임을 재사용 → 반복과 동일한 성능!
    
    # 일반 재귀 (스택 O(n)):
    def factorial(n):
        if n == 0: return 1
        return n * factorial(n-1)    ← 곱셈이 마지막 → TCO 불가
    
    # 꼬리 재귀 (스택 O(1), TCO 시):
    def factorial(n, acc=1):
        if n == 0: return acc
        return factorial(n-1, n*acc)  ← 재귀가 마지막 → TCO 가능!
    
    Haskell, Scheme: TCO 보장
    Python, Java: TCO 미지원 → 깊은 재귀 시 스택 오버플로
```

### 8.2 예외 처리 — 왜 필요한가

```
오류가 발생한 곳과 처리할 곳이 다를 수 있다.
  파일 읽기 함수: "파일이 없다"는 오류를 발견
  호출한 함수: "없으면 기본값을 사용"하기로 결정
  
  → 오류를 발견한 곳에서 처리 방법을 모른다
  → 오류를 호출 스택 위로 "전파"해야 한다 = 예외 던지기

  try { ... } catch (Exception e) { ... } finally { ... }
  
  try: 예외가 발생할 수 있는 코드
  catch: 예외 처리 (타입별로 분기 가능)
  finally: 예외 여부와 무관하게 항상 실행 (자원 정리)

  대안: Result 타입 (Rust, Haskell)
    함수가 성공(Ok) 또는 실패(Err)를 반환. 예외 없이 명시적으로 처리.
    → 예외: 암시적 제어 흐름 (어디서 터질지 모름)
    → Result: 명시적 (반환값을 처리해야 컴파일됨) → 더 안전하지만 장황.
```

## 9. 매개변수 전달 — "함수에 값을 어떻게 넘기는가"

```
🔴 주요 전달 방식:

  값 전달 (Pass by Value):
    값의 복사본을 전달. 원본에 영향 없음.
    C의 기본, Java의 기본형(int, double).

  참조 전달 (Pass by Reference):
    변수 자체의 참조(주소)를 전달. 원본이 변경됨.
    C++의 &, C#의 ref.

  공유에 의한 호출 (Pass by Sharing / 객체 참조 전달):
    "참조의 값"을 전달. 객체 내부는 변경 가능, 참조 자체는 교체 불가.
    Java의 객체, Python, JavaScript.
    
    → 가장 혼란스러운 방식. "Java는 값 전달이다"가 맞는 이유:
      참조(=주소값)를 값으로 전달한다.
      함수 안에서 obj = new Object()해도 바깥의 변수는 안 바뀜.
      함수 안에서 obj.setX(5)하면 바깥 객체의 x도 바뀜 (같은 객체를 가리키므로).

왜 여러 방식이 있는가:
  값 전달: 안전 (원본 보호), 비용 (큰 객체 복사 비쌈)
  참조 전달: 효율 (복사 안 함), 위험 (원본 변경 가능)
  → 트레이드오프. 언어마다 기본 방식이 다르다.
```

## 10. 컴파일러와 인터프리터 — 코드가 실행되는 방법

### 10.1 컴파일러 전체 구조

```
🔴 컴파일러 파이프라인:

  소스 코드
    ↓ [어휘 분석 (Lexer)] ← 정규식, DFA (Ch.04)
  토큰 스트림
    ↓ [구문 분석 (Parser)] ← CFG, 푸시다운 오토마타 (Ch.04)
  AST
    ↓ [의미 분석] ← 타입 검사, 심볼 테이블
  주석 AST (Annotated AST)
    ↓ [중간 코드 생성] ← SSA, 3주소 코드
  IR (Intermediate Representation)
    ↓ [최적화] ← 상수 폴딩, 루프 불변 코드 이동, 인라이닝
  최적화된 IR
    ↓ [코드 생성] ← 레지스터 할당, 명령어 선택
  기계어 / 바이트코드

왜 중간 표현(IR)을 쓰는가:
  m개 언어 × n개 플랫폼 = m×n개 컴파일러가 필요.
  IR을 사용하면: m개 프론트엔드 + n개 백엔드 = m+n개만 필요!
  
  LLVM: 이 원리의 대표적 구현.
    C, C++, Rust, Swift → LLVM IR → x86, ARM, WASM, ...
    프론트엔드만 만들면 모든 플랫폼을 지원!
```

### 10.2 주요 최적화 — 왜 컴파일러가 인간보다 나은가

```
🟢 [유도 가능 — 원리를 이해하면 왜 최적화가 가능한지 알 수 있다]

  상수 폴딩 (Constant Folding):
    x = 3 * 4 → x = 12  (컴파일 시 계산)

  공통 부분식 제거 (CSE):
    a = b * c + d
    e = b * c + f  → temp = b * c; a = temp + d; e = temp + f

  루프 불변 코드 이동 (LICM):
    for i in range(n):
        x = y * z     ← 루프 안에서 변하지 않음
        a[i] = x + i
    → x = y * z; for i in range(n): a[i] = x + i

  인라이닝 (Inlining):
    작은 함수의 본문을 호출 지점에 삽입 → 함수 호출 오버헤드 제거

  데드 코드 제거 (Dead Code Elimination):
    절대 실행되지 않는 코드 제거
```

### 10.3 인터프리터와 JIT — 왜 구분이 흐려지는가

```
🔴 세 가지 실행 방식:

  (1) 순수 컴파일 (AOT): 실행 전에 전부 기계어로 변환.
      C, C++, Rust, Go.
      장점: 실행 시 최고 속도. 단점: 컴파일 시간, 플랫폼 의존.

  (2) 순수 인터프리터: 소스를 한 줄씩 읽어 실행.
      초기 Python, Bash.
      장점: 즉시 실행, 플랫폼 독립. 단점: 느림 (10~100배).

  (3) JIT (Just-In-Time) 컴파일: 실행 중 "핫 코드"를 기계어로 컴파일.
      JVM (Java), V8 (JavaScript), PyPy (Python).
      장점: AOT에 가까운 속도 + 인터프리터의 유연성
      
      왜 JIT가 가능한가:
        프로그램의 90%의 시간이 10%의 코드에서 소비됨 (지역성!).
        그 10%만 컴파일하면 전체의 90%가 빨라진다.
        나머지 90% 코드는 인터프리트 — 컴파일 비용 절약.

  현대 추세:
    순수한 인터프리터/컴파일러는 드물다.
    대부분 하이브리드: 바이트코드 컴파일 + JIT.
    Java: .java → .class(바이트코드) → JVM이 JIT으로 기계어 변환.
    JavaScript: V8이 AST → 바이트코드 → JIT → 최적화된 기계어.
```

## 11. 람다 대수 — 함수형 프로그래밍의 수학적 기반

```
🔴 [정의] 람다 대수 (Lambda Calculus, Alonzo Church, 1930s):
  계산을 "함수의 정의와 적용"만으로 표현하는 형식 체계.

  세 가지 구성 요소만 존재:
    변수:    x
    추상화:  λx.M    ("x를 받아 M을 반환하는 함수")
    적용:    M N     ("M에 N을 적용")

  예시:
    항등 함수:  λx.x        (입력을 그대로 반환)
    상수 함수:  λx.λy.x     (첫 인수를 반환, 두 번째 무시)
    적용:      (λx.x+1) 3 = 3+1 = 4

왜 이것이 중요한가:
  (1) 튜링 머신과 동등한 계산 능력 (Church-Turing 논제)
      → "계산 가능한 모든 것"을 람다 대수로 표현 가능
  (2) 모든 함수형 언어의 이론적 기반
      Haskell, Lisp, ML, Scala의 핵심 원리
  (3) 프로그래밍 언어의 의미론을 정의하는 도구

🔵 [CS 연결]
  Python: lambda x: x + 1
  JavaScript: (x) => x + 1
  Java: x -> x + 1
  → 이 "람다 표현식"의 이름이 람다 대수에서 온 것!
  
  커링 (Currying):
    f(x, y) = x + y → f(x) = λy.(x + y)
    다인수 함수를 단인수 함수의 체인으로 변환.
    → 부분 적용(partial application)의 기반.
    → 이름은 Haskell Curry에서.
```

## 12. 현대 언어 트렌드

```
🔵 각 언어가 해결하려는 문제:

  Rust: "안전하면서도 빠른 시스템 프로그래밍"
    → 소유권으로 GC 없이 메모리 안전 + C/C++ 수준 성능

  Go: "단순하고 빠른 서버 사이드"
    → 고루틴(경량 스레드) + 채널 = 쉬운 동시성

  Kotlin: "Java를 더 좋게"
    → 널 안전성, 코루틴, 간결한 문법. Android 공식 언어.

  TypeScript: "JavaScript를 안전하게"
    → 점진적 정적 타입. JS 생태계 + 타입 검사.

  Swift: "Objective-C를 대체"
    → 안전, 빠름, 표현력. Apple 생태계.

  WebAssembly (WASM): "브라우저에서 네이티브 성능"
    → 다양한 언어(C, Rust, Go)의 컴파일 타겟. 브라우저 밖에서도 사용 확대.

공통 트렌드:
  (1) 타입 안전성 강화 (Null 안전, 대수적 타입)
  (2) 함수형 기능 채용 (일급 함수, 패턴 매칭, 불변성)
  (3) 동시성 지원 내장 (async/await, 고루틴, 코루틴)
  (4) 메모리 안전성 (GC 또는 소유권 시스템)
```

## 14. 정리 — PLT를 관통하는 원리

```
[원리 1] 패러다임 = 사고의 틀. 명령형(상태 변이) vs 함수형(값 변환).
  → 하나의 정답은 없다. 문제에 맞는 패러다임을 선택.

[원리 2] 구문(형태)과 의미(행동)의 분리.
  → BNF로 구문 정의, 의미론(조작/표시/공리)으로 행동 정의.

[원리 3] 바인딩 시점 = 유연성 vs 안전성 트레이드오프.
  → 빠른 바인딩(정적): 안전, 효율. 늦은 바인딩(동적): 유연.

[원리 4] 타입 시스템 = "의미 있는 연산만 허용"하는 규칙.
  → 정적 vs 동적, 강한 vs 약한, 추론 vs 명시.

[원리 5] 클로저 = 함수 + 환경. 상태 캡슐화의 핵심.

[원리 6] 메모리 관리: 수동(제어) vs GC(안전) vs 소유권(둘 다).
  → 세대별 GC: "대부분 금방 죽는다"는 관찰이 핵심.

[원리 7] 컴파일러 = 프론트엔드(언어 의존) + IR + 백엔드(플랫폼 의존).
  → IR로 분리하면 m+n개로 m×n 문제를 해결.

[원리 8] 람다 대수 = 계산의 수학적 본질. 함수의 정의와 적용만으로 모든 계산 표현.

외워야 할 것:
  🔴 주요 패러다임과 대표 언어
  🔴 정적 vs 동적 타입의 트레이드오프
  🔴 3가지 의미론 (조작적, 표시적, 공리적)
  🔴 정적 vs 동적 스코프의 차이
  🔴 GC 알고리즘 3가지 (참조 카운팅, Mark-and-Sweep, 세대별)
  🔴 컴파일러 파이프라인 단계
  🔴 람다 대수의 3가지 구성 요소

유도할 수 있는 것:
  🟢 클로저의 동작 (스코프 규칙에서)
  🟢 커링이 가능한 이유 (함수가 일급 객체이면)
  🟢 타입 추론의 원리 (사용 맥락에서 제약 수집 → 통합)
  🟢 TCO가 작동하는 조건 (마지막 연산이 재귀 호출)
  🟢 JIT가 효과적인 이유 (지역성: 10% 코드가 90% 시간)
```
