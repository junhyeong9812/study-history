└──────────────┴──────────────────────────┴──────────────────────────────────┘

## 1. 출발점: 왜 DBMS가 필요한가

### 1.1 파일로 데이터를 관리하면 어떻게 되는가

```
파일 기반 데이터 관리의 문제:

  (1) 데이터 중복: 같은 정보가 여러 파일에 중복 저장
      → 하나를 수정하면 나머지도 모두 수정해야 → 불일치 발생!
  
  (2) 데이터 종속: 데이터 형식이 바뀌면 프로그램도 전부 수정
      → 파일 구조와 프로그램이 강하게 결합
  
  (3) 동시 접근 불가: 여러 사용자가 동시에 파일을 수정하면 충돌
  
  (4) 보안/무결성 부재: 누구든 파일을 직접 수정 가능, 제약 조건 검증 없음
  
  (5) 장애 복구 어려움: 쓰기 도중 전원이 꺼지면 데이터 손상

DBMS는 이 모든 문제를 체계적으로 해결한다:
  → 중복 제거 (정규화), 독립성 (스키마 분리), 동시성 (트랜잭션),
    보안 (권한 관리), 무결성 (제약 조건), 복구 (로그 기반)
```

### 1.2 3단계 스키마 구조 — 왜 이렇게 나누는가

```
🔴 [정의] ANSI/SPARC 3단계 구조:

  외부 스키마 (External): 각 사용자/앱이 보는 뷰 (필요한 부분만)
  개념 스키마 (Conceptual): 전체 DB의 논리적 구조 (무엇이 저장되는가)
  내부 스키마 (Internal): 실제 물리적 저장 방식 (어떻게 저장되는가)

왜 나누는가:
  데이터 독립성을 달성하기 위해!
  
  물리적 독립성: 저장 방식을 바꿔도 논리 구조는 안 바뀜
    예: 인덱스 추가/제거, 파일 구조 변경 → 앱 코드 수정 불필요
  
  논리적 독립성: 전체 구조를 바꿔도 각 사용자의 뷰는 안 바뀜
    예: 테이블 분할 → 기존 뷰로 접근하는 앱은 영향 없음

  이것은 소프트웨어 공학의 "관심사 분리" 원칙과 같다.
```

## 2. 관계형 모델 — 왜 "테이블"인가

### 2.1 관계형 모델의 핵심 아이디어

```
🔴 [정의] E.F. Codd (1970):
  모든 데이터를 "테이블(관계, relation)"로 표현한다.

  릴레이션 = 속성(열)들의 집합으로 정의된 튜플(행)들의 집합

  students 테이블:
  ┌─────┬──────┬──────┬──────┐
  │ id  │ name │ dept │ gpa  │
  ├─────┼──────┼──────┼──────┤
  │ 1   │ 김철수│ CS   │ 3.8  │
  │ 2   │ 이영희│ EE   │ 3.5  │
  │ 3   │ 박민수│ CS   │ 3.9  │
  └─────┴──────┴──────┴──────┘

왜 테이블인가:
  수학적으로 테이블 = 집합의 카르테시안 곱의 부분집합 (Ch.04)
  
  students ⊆ INT × VARCHAR × VARCHAR × DECIMAL
  
  집합론의 성질이 그대로 적용된다:
  → 합집합, 교집합, 차집합 등의 연산이 수학적으로 정의됨
  → 이것이 SQL 질의의 이론적 기반

  릴레이션의 성질 (집합이므로):
  → 튜플의 순서는 없다 (집합에 순서 없음)
  → 중복 튜플은 없다 (집합에 중복 없음)
  → 속성값은 원자적이어야 한다 (1NF의 근거)
```

### 2.2 키의 종류 — 왜 이렇게 많은가

```
🔴 [정의]
  슈퍼키 (Super Key): 튜플을 유일하게 식별하는 속성 집합
    예: {id}, {id, name}, {id, name, dept}, ...
    → 슈퍼키에 속성을 더 추가해도 여전히 슈퍼키
  
  후보키 (Candidate Key): 최소한의 슈퍼키 (더 줄이면 유일성을 잃음)
    예: {id}는 후보키. {id, name}은 아님 (id만으로도 충분)
  
  기본키 (Primary Key, PK): 후보키 중 하나를 선택하여 "대표"로 지정
    규칙: NULL 불가, 변경 불가(원칙), 테이블당 하나
  
  외래키 (Foreign Key, FK): 다른 테이블의 기본키를 참조하는 속성
    → 테이블 간의 관계를 표현하는 핵심 도구

왜 외래키가 중요한가:
  "학생이 속한 학과"를 표현하려면?
  
  students:                  departments:
  ┌────┬──────┬─────────┐   ┌─────────┬────────┐
  │ id │ name │ dept_id │   │ dept_id │ dept_name│
  ├────┼──────┼─────────┤   ├─────────┼────────┤
  │ 1  │ 김철수│   10    │   │   10    │ CS     │
  │ 2  │ 이영희│   20    │   │   20    │ EE     │
  └────┴──────┴─────────┘   └─────────┴────────┘
  
  students.dept_id는 departments.dept_id를 참조하는 외래키.
  
  참조 무결성: FK 값은 참조된 테이블에 반드시 존재해야 한다.
    → dept_id = 99를 넣으면? → 거부! (없는 학과 참조 불가)
    → 데이터의 일관성을 보장하는 규칙
```

## 3. SQL — 데이터베이스의 언어

### 3.1 SQL이란 — 왜 "선언적"인가

```
🔴 [핵심 특성] SQL은 선언적(declarative) 언어이다.
  "무엇을(what)" 원하는지만 말하고, "어떻게(how)" 찾는지는 DBMS가 결정.

  SQL:  SELECT name FROM students WHERE gpa > 3.5
  의미: "GPA가 3.5보다 큰 학생의 이름을 달라"
  
  프로그래밍이었다면:
    result = []
    for student in students:
        if student.gpa > 3.5:
            result.append(student.name)
  
  왜 선언적이 좋은가:
    (1) 사용자는 "무엇을"에만 집중 → 생산성 향상
    (2) DBMS의 옵티마이저가 최적 실행 계획을 선택 → 성능 최적화
        인간보다 DBMS가 인덱스 활용, 조인 순서 등을 더 잘 결정한다.
```

### 3.2 SQL 핵심 구문 — 각각 왜 이 형태인가

```
🔴 SELECT (조회) — SQL의 핵심:

  SELECT 열_목록     ← 어떤 정보를 원하는가
  FROM 테이블_목록   ← 어디서 가져오는가
  WHERE 조건         ← 어떤 행만 원하는가
  GROUP BY 그룹_기준  ← 어떻게 묶을 것인가
  HAVING 그룹_조건    ← 묶은 후 어떤 그룹만 원하는가
  ORDER BY 정렬_기준  ← 결과를 어떤 순서로
  LIMIT 개수          ← 몇 개만

  실행 순서 (작성 순서와 다르다!):
    FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
    
    왜 이 순서인가:
      먼저 어디서(FROM) 가져와서, 조건 필터링(WHERE)하고,
      그룹으로 묶고(GROUP BY), 그룹 필터링(HAVING)하고,
      원하는 열만 추출(SELECT)하고, 정렬(ORDER BY)하고, 제한(LIMIT).
      
      → 데이터를 점점 좁혀나가는 파이프라인.
```

### 3.3 JOIN — 왜 여러 종류가 있는가

```
🔴 JOIN: 두 테이블을 결합하는 연산

  students:              enrollments:
  ┌────┬──────┐          ┌────────────┬───────────┐
  │ id │ name │          │ student_id │ course_id │
  ├────┼──────┤          ├────────────┼───────────┤
  │ 1  │ 김철수│          │     1      │   CS101   │
  │ 2  │ 이영희│          │     1      │   CS201   │
  │ 3  │ 박민수│          │     3      │   CS101   │
  └────┴──────┘          └────────────┴───────────┘

  INNER JOIN: 양쪽 모두에 매칭되는 행만
    SELECT s.name, e.course_id 
    FROM students s INNER JOIN enrollments e ON s.id = e.student_id
    → 김철수-CS101, 김철수-CS201, 박민수-CS101 (이영희는 수강 없으므로 제외)

  LEFT JOIN: 왼쪽 테이블의 모든 행 + 매칭되는 오른쪽 행 (없으면 NULL)
    → 이영희도 포함, course_id = NULL

  RIGHT JOIN: 오른쪽 테이블의 모든 행 + 매칭되는 왼쪽 행

  FULL OUTER JOIN: 양쪽 모든 행 (매칭 안 되면 NULL)

왜 여러 종류인가:
  "매칭 안 되는 데이터를 어떻게 처리할 것인가"에 따라 결과가 달라진다.
  - "수강 신청한 학생만 보고 싶다" → INNER JOIN
  - "수강 안 한 학생도 포함해서 보고 싶다" → LEFT JOIN
  → 요구 사항에 따라 적절한 조인을 선택해야 정확한 결과를 얻는다.
```

### 3.4 서브쿼리와 집계 — 왜 필요한가

```
집계 함수: 여러 행을 하나의 값으로 축약
  COUNT(*), SUM(col), AVG(col), MAX(col), MIN(col)

  SELECT dept, AVG(gpa) FROM students GROUP BY dept HAVING AVG(gpa) > 3.5

  왜 WHERE가 아니라 HAVING인가:
    WHERE: 개별 행을 필터링 (GROUP BY 전에 적용)
    HAVING: 그룹을 필터링 (GROUP BY 후에 적용)
    → AVG(gpa)는 그룹을 만든 후에야 계산 가능 → HAVING에서만 사용

서브쿼리: 쿼리 안의 쿼리
  SELECT name FROM students 
  WHERE dept_id IN (SELECT dept_id FROM departments WHERE location = '서울')
  
  왜 필요한가: 한 쿼리의 결과를 다른 쿼리의 조건으로 사용.
  → 복잡한 질의를 단계별로 분해하여 표현.
```

## 4. 정규화 — 왜 테이블을 쪼개야 하는가

### 4.1 이상 현상 — 정규화하지 않으면 무슨 일이 생기는가

```
비정규화된 테이블:
  ┌────┬──────┬──────┬───────────┬───────────┐
  │ id │ name │ dept │ dept_head │ dept_phone │
  ├────┼──────┼──────┼───────────┼───────────┤
  │ 1  │ 김철수│ CS   │ 이교수    │ 1234      │
  │ 2  │ 이영희│ EE   │ 박교수    │ 5678      │
  │ 3  │ 박민수│ CS   │ 이교수    │ 1234      │
  └────┴──────┴──────┴───────────┴───────────┘

세 가지 이상(Anomaly):

  삽입 이상: 학생 없는 새 학과(ME)를 추가하려면?
    → id, name이 NULL이어야 → PK가 NULL → 불가!
    → 학과 정보를 저장할 곳이 없다!
  
  갱신 이상: CS 학과장이 바뀌면?
    → 김철수와 박민수 행을 모두 수정해야.
    → 하나만 수정하면 불일치!
  
  삭제 이상: 이영희가 자퇴하면?
    → 이영희 행을 삭제하면 EE 학과 정보도 함께 사라진다!

🔴 원인: "서로 다른 개념(학생과 학과)이 하나의 테이블에 섞여 있기 때문"
  → 해결: 정규화로 분리!
```

### 4.2 함수 종속 — 정규화의 수학적 도구

```
🔴 [정의] 함수 종속 (Functional Dependency, FD):
  X → Y: "X의 값이 결정되면 Y의 값이 유일하게 결정된다"

  id → name       (학번이 같으면 이름도 같다)
  dept → dept_head (학과가 같으면 학과장도 같다)
  
  {id, course} → grade  (학번+과목이 같으면 성적이 결정된다)

왜 FD가 중요한가:
  FD를 분석하면 "어떤 속성이 어떤 속성에 의존하는가"를 파악할 수 있다.
  이를 기반으로 "관련 있는 것끼리 묶고, 관련 없는 것은 분리"한다 = 정규화.
```

### 4.3 정규형 — 왜 이 순서인가

```
🔴 [정의] 각 정규형은 이전 것을 포함한다: 1NF ⊂ 2NF ⊂ 3NF ⊂ BCNF

1NF (제1 정규형):
  모든 속성값이 원자적(atomic)이다. 하나의 칸에 하나의 값만.
  
  위반: 전화번호 칸에 "010-1234, 010-5678" → 1NF 위반!
  해결: 행을 분리하거나 별도 테이블로.
  
  왜 이것이 첫 번째인가:
    관계형 모델의 기본 가정이다 (릴레이션 = 원자값의 집합).
    이것이 안 되면 나머지 정규화가 의미 없다.

2NF (제2 정규형):
  1NF + "부분 함수 종속 제거"
  
  부분 함수 종속: 복합키의 일부만으로 결정되는 속성이 있으면 위반.
    {student_id, course_id} → grade  ✓ (두 키 모두 필요)
    {student_id, course_id} → student_name  ✗ (student_id만으로 결정!)
  
  해결: student_name을 별도 테이블로 분리.
  
  왜: 부분 종속이 있으면 → 키의 일부가 반복 → 갱신 이상 발생.

3NF (제3 정규형):
  2NF + "이행 함수 종속 제거"
  
  이행 종속: A → B → C에서 A → C가 B를 거쳐 간접적으로 결정.
    id → dept → dept_head
    id는 dept를 결정하고, dept는 dept_head를 결정.
    → id → dept_head는 이행 종속.
  
  해결: dept → dept_head를 별도 테이블로 분리.
  
  왜: 이행 종속이 있으면 → 중간 속성(dept) 관련 정보가 중복 → 이상 발생.

BCNF (보이스-코드 정규형):
  "모든 결정자가 후보키"
  3NF보다 엄격. 모든 FD X → Y에서 X가 반드시 슈퍼키.
  
  3NF와 BCNF의 차이가 나는 경우는 드물지만,
  드물게 3NF인데 BCNF가 아닌 경우가 있다.

실무에서:
  보통 3NF 또는 BCNF까지 정규화한다.
  그 이상(4NF, 5NF)은 매우 특수한 경우에만 필요.
  
  🔴 반정규화 (Denormalization):
    정규화의 역과정. 의도적으로 중복을 허용.
    왜: 조인이 비싸면 성능을 위해 중복을 두기도 한다.
    → 정규화 = 설계의 정확성, 반정규화 = 성능 최적화. 트레이드오프!
```

## 5. 트랜잭션 — "전부 아니면 전무"

### 5.1 트랜잭션이란 — 왜 이 개념이 필요한가

```
🔴 [정의] 트랜잭션: 하나의 논리적 작업 단위. 전부 성공하거나 전부 실패해야 한다.

예시: 계좌 이체
  (1) A 계좌에서 10만원 차감
  (2) B 계좌에 10만원 추가
  
  (1)만 실행되고 (2)에서 실패하면? → 10만원이 증발!
  → 두 연산이 "하나의 단위"로 묶여야 한다 = 트랜잭션.
  → 실패하면 (1)도 되돌린다 (rollback).
```

### 5.2 ACID — 왜 이 네 가지인가

```
🔴 [정의] ACID 속성:

  Atomicity (원자성):
    트랜잭션은 전부 실행되거나 전부 취소된다.
    "반만 실행"은 없다.
    → Undo 로그로 구현: 실패 시 변경 사항을 역순으로 되돌린다.

  Consistency (일관성):
    트랜잭션 전후로 DB가 모든 제약 조건을 만족한다.
    예: "잔고 ≥ 0" 제약 → 이체 후에도 음수가 되지 않아야.
    → 제약 조건 검사 + 트리거로 보장.

  Isolation (격리성):
    동시에 실행되는 트랜잭션들이 서로 간섭하지 않는다.
    "혼자 실행한 것과 결과가 같아야" 한다.
    → 잠금(Lock) 또는 MVCC로 구현.

  Durability (지속성):
    커밋된 트랜잭션의 결과는 영구적으로 보존된다.
    전원이 꺼져도 데이터가 살아남아야 한다.
    → WAL(Write-Ahead Log)로 구현: 디스크에 로그를 먼저 쓴다.

왜 이 네 가지가 필요한가:
  하나라도 없으면 데이터를 "신뢰"할 수 없다.
  
  원자성 없으면: 반만 실행된 불완전한 상태가 남음
  일관성 없으면: 규칙이 깨진 데이터가 저장됨
  격리성 없으면: 동시 접근 시 결과가 예측 불가능 (경쟁 상태! Ch.12)
  지속성 없으면: 커밋해도 날아갈 수 있음 → 신뢰 불가
```

### 5.3 격리 수준 — 왜 여러 단계가 있는가

```
🔴 완벽한 격리(Serializable)는 성능이 나쁘다.
  → 현실에서는 "어느 정도의 간섭을 허용"하여 성능을 높인다.
  → 격리 수준이 낮을수록: 성능 ↑, 데이터 정확성 ↓

  ┌─────────────────┬──────────┬───────────────┬──────────┐
  │ 격리 수준        │ Dirty    │ Non-Repeatable│ Phantom  │
  │                 │ Read     │ Read          │ Read     │
  ├─────────────────┼──────────┼───────────────┼──────────┤
  │ Read Uncommitted│ 가능 ✗   │ 가능 ✗        │ 가능 ✗   │
  │ Read Committed  │ 방지 ✓   │ 가능 ✗        │ 가능 ✗   │
  │ Repeatable Read │ 방지 ✓   │ 방지 ✓        │ 가능 ✗   │
  │ Serializable    │ 방지 ✓   │ 방지 ✓        │ 방지 ✓   │
  └─────────────────┴──────────┴───────────────┴──────────┘

  Dirty Read: 다른 트랜잭션이 아직 커밋하지 않은 데이터를 읽음
    → 그 트랜잭션이 롤백하면? → 읽은 데이터가 "없던 일"이 됨!
  
  Non-Repeatable Read: 같은 행을 두 번 읽었는데 값이 달라짐
    → 사이에 다른 트랜잭션이 수정+커밋한 것
  
  Phantom Read: 같은 조건으로 두 번 조회했는데 행의 수가 달라짐
    → 사이에 다른 트랜잭션이 삽입/삭제한 것

  🔵 MySQL InnoDB 기본: Repeatable Read
     PostgreSQL 기본: Read Committed
```

### 5.4 동시성 제어 — 어떻게 격리를 구현하는가

```
🔴 방법 1: 잠금 기반 (Lock-based)

  공유 잠금 (S-lock, Shared): 읽기 잠금. 여러 트랜잭션이 동시 보유 가능.
  배타 잠금 (X-lock, Exclusive): 쓰기 잠금. 하나만 보유 가능.

  2PL (Two-Phase Locking):
    Growing 단계: 잠금만 획득, 해제 안 함
    Shrinking 단계: 잠금만 해제, 획득 안 함
    
    왜 2단계인가:
      잠금을 "중간에 풀었다 다시 잡으면" 다른 트랜잭션이 끼어들 수 있다
      → 직렬 가능성(serializability)이 깨짐
      → Growing에서 필요한 잠금을 다 잡고, Shrinking에서 다 풀면
         끼어들 여지가 없다 → 직렬 가능성 보장
    
    문제: 데드락 가능! (Ch.12와 동일)
      → 데드락 탐지: 대기 그래프에서 사이클 탐색
      → 발견 시: 한 트랜잭션을 롤백

🔴 방법 2: MVCC (Multi-Version Concurrency Control)
  
  핵심: 데이터의 여러 버전을 유지한다.
  읽기는 "자기가 시작했을 때의 스냅샷"을 본다.
  쓰기는 새 버전을 만든다.
  
  → 읽기와 쓰기가 서로 블로킹하지 않는다!
  → 읽기 성능이 대폭 향상.
  
  왜 이것이 현대 DB의 표준인가:
    잠금 기반: 읽기가 쓰기를 블로킹 → 동시성 ↓
    MVCC: 읽기는 항상 즉시 가능 → 동시성 ↑
    
    대가: 오래된 버전을 정리(vacuum/garbage collection)해야 함.
  
  🔵 PostgreSQL, MySQL InnoDB, Oracle 모두 MVCC 사용.
```

### 5.5 회복 — 장애에서 살아남기

```
🔴 WAL (Write-Ahead Logging):
  "데이터를 수정하기 전에, 반드시 로그를 먼저 디스크에 쓴다"

  왜 이 순서인가:
    데이터를 먼저 쓰고 장애 발생 → 무엇이 바뀌었는지 모름 → 복구 불가
    로그를 먼저 쓰면 → 장애 후 로그를 보고 복구 가능!

  복구 과정:
    Redo: 커밋된 트랜잭션의 변경을 다시 적용 (지속성 보장)
    Undo: 커밋 안 된 트랜잭션의 변경을 되돌림 (원자성 보장)

  체크포인트: 특정 시점까지의 데이터를 디스크에 확실히 기록.
    → 복구 시 체크포인트 이후의 로그만 재생하면 됨 → 복구 속도 ↑

  🔵 Ch.12 파일 시스템의 저널링과 같은 원리!
```

## 6. 인덱싱 — 검색을 빠르게

### 6.1 왜 인덱스가 필요한가

```
인덱스 없이 검색:
  SELECT * FROM students WHERE name = '김철수'
  → 모든 행을 순차 스캔 → O(n) → 100만 행이면 느리다!

인덱스가 있으면:
  name에 인덱스 → B+ 트리에서 '김철수'를 찾음 → O(log n)
  → 100만 행이면 ~20번의 비교로 끝!

인덱스 = "책의 색인(찾아보기)"과 같다.
  "김철수"를 찾으려면 책 전체를 읽는 대신, 뒤의 색인을 보고 페이지로 점프.
```

### 6.2 인덱스 종류

```
🔴 B+ 트리 인덱스 (Ch.09 §8에서 상세):
  대부분 RDBMS의 기본 인덱스.
  등가 검색: O(log n), 범위 검색: O(log n + 결과 수)
  
  왜 B+ 트리인가 (다시 정리):
    디스크 I/O 최소화 (높은 분기 수 → 낮은 높이)
    리프 노드가 연결 → 범위 검색에 효율적
    삽입/삭제 시 자동 균형 유지

🔴 해시 인덱스:
  등가 검색: O(1). 범위 검색: 불가!
  → "정확히 이 값"을 찾을 때만 사용.

🔴 클러스터드 인덱스 (Clustered Index):
  데이터의 물리적 순서 = 인덱스 순서.
  테이블당 하나만 가능. (데이터 자체의 순서는 하나뿐이니까)
  → 범위 검색이 매우 빠름 (물리적으로 연속 저장)

🔴 비클러스터드 인덱스 (Non-Clustered):
  별도의 인덱스 구조가 데이터의 위치(포인터)를 저장.
  여러 개 가능.

🔴 복합 인덱스 (Composite Index):
  여러 열을 조합한 인덱스. (col1, col2, col3)
  
  🔴 최좌선 접두사 원칙 (Leftmost Prefix Rule):
    (A, B, C) 인덱스로 검색 가능한 것:
    ✓ A만, ✓ A+B, ✓ A+B+C
    ✗ B만, ✗ C만, ✗ B+C
    
    왜: B+ 트리가 A → B → C 순으로 정렬되므로,
    A 없이 B를 찾으려면 전체 스캔해야 한다.
    
    비유: 전화번호부가 "성 → 이름 → 도시" 순으로 정렬되어 있을 때,
    "성"을 모르면 "이름"으로는 찾을 수 없다.

인덱스의 비용:
  검색: 빠르다!
  삽입/삭제: 느려진다 (인덱스도 함께 업데이트해야)
  공간: 추가 저장 공간 필요
  
  → 인덱스 = 읽기 성능 ↑, 쓰기 성능 ↓의 트레이드오프.
  → 자주 검색되는 열에만 인덱스를 만들어야 한다.
```

## 7. 쿼리 처리와 최적화

```
🔵 SQL 쿼리가 실행되는 과정:

  SQL 텍스트
    ↓ 파싱 (Parser)
  파스 트리
    ↓ 검증 (스키마 확인)
  관계 대수 표현
    ↓ 최적화 (Optimizer) ← 핵심!
  실행 계획
    ↓ 실행 (Executor)
  결과

왜 옵티마이저가 중요한가:

  같은 쿼리를 실행하는 방법이 수십~수백 가지.
  
  SELECT * FROM A JOIN B JOIN C WHERE ...
  
  조인 순서: A×B×C, A×C×B, B×A×C, ...  → n! 가지
  각 조인 방식: 중첩 루프, 해시 조인, 소트-머지 조인
  인덱스 사용 여부: 각 테이블에 대해 선택
  
  어떤 계획은 0.01초, 어떤 계획은 10시간이 걸릴 수 있다!
  → 옵티마이저가 비용을 추정하여 최적 계획을 선택.
  
  🔵 EXPLAIN 명령으로 옵티마이저의 실행 계획을 확인할 수 있다.
```

## 8. 분산 데이터베이스와 NoSQL

### 8.1 왜 분산이 필요한가

```
단일 서버의 한계:
  (1) 용량: 한 서버의 디스크에 다 담을 수 없는 양
  (2) 성능: 한 서버의 CPU/메모리로 처리할 수 없는 트래픽
  (3) 가용성: 서버가 죽으면 서비스 중단

해결: 데이터를 여러 서버에 분산.
  샤딩(Sharding): 데이터를 분할하여 여러 서버에 저장. 용량↑ 성능↑
  복제(Replication): 같은 데이터를 여러 서버에 복제. 가용성↑ 읽기 성능↑
```

### 8.2 CAP 정리 — 왜 세 가지를 동시에 못 가지는가

```
🔴 [정리] CAP (Brewer, 2000):
  분산 시스템에서 다음 세 가지를 동시에 모두 만족할 수 없다:

  Consistency (일관성): 모든 노드가 같은 데이터를 본다
  Availability (가용성): 모든 요청이 응답을 받는다 (에러 없이)
  Partition tolerance (분할 허용): 네트워크 분할이 발생해도 시스템이 작동

왜 세 가지가 동시에 불가능한가:

  네트워크 분할 상황:
    서버 A와 서버 B 사이 네트워크가 끊김.
    
    일관성을 유지하려면:
      A에 쓴 데이터를 B에도 반영해야 → 네트워크 끊김 → 불가!
      → 응답을 거부(가용성 포기) 또는 B가 오래된 데이터를 반환(일관성 포기)
    
    가용성을 유지하려면:
      양쪽 모두 응답해야 → B는 A의 최신 데이터를 모름 → 일관성 포기
    
    → P(분할)는 현실적으로 피할 수 없으므로 (네트워크는 반드시 실패한다),
      실질적 선택은 C vs A:

  CP: 일관성 + 분할 허용 (가용성 포기)
    예: MongoDB (기본), HBase, Zookeeper
    "응답은 못 해도, 잘못된 데이터는 안 준다"

  AP: 가용성 + 분할 허용 (일관성 포기)
    예: Cassandra, DynamoDB, CouchDB
    "항상 응답하지만, 약간 오래된 데이터일 수 있다"
    → Eventually Consistent (결과적 일관성): 시간이 지나면 일관성 회복
```

### 8.3 NoSQL — 왜 관계형만으로는 부족한가

```
🔴 NoSQL의 존재 이유:
  관계형 DB의 한계:
    (1) 스키마 변경이 어렵다 (ALTER TABLE은 큰 테이블에서 매우 느림)
    (2) 수평 확장이 어렵다 (조인이 여러 서버에 걸치면 비쌈)
    (3) 비정형 데이터에 부적합 (JSON, 그래프 등)

  NoSQL = "특정 사용 패턴에 최적화된 데이터베이스"

🔴 NoSQL 유형별 적합한 사용 사례:

  ┌──────────────┬────────────────┬────────────────────────┐
  │ 유형          │ 대표 DB         │ 적합한 경우              │
  ├──────────────┼────────────────┼────────────────────────┤
  │ 키-값         │ Redis, DynamoDB│ 캐시, 세션, 설정         │
  │ (Key-Value)  │                │ 단순 조회가 대부분        │
  ├──────────────┼────────────────┼────────────────────────┤
  │ 문서          │ MongoDB        │ 유연한 스키마, JSON 저장  │
  │ (Document)   │                │ 카탈로그, 사용자 프로필    │
  ├──────────────┼────────────────┼────────────────────────┤
  │ 컬럼 패밀리   │ Cassandra,     │ 대규모 쓰기, 시계열 데이터│
  │ (Wide Column)│ HBase          │ IoT, 로그               │
  ├──────────────┼────────────────┼────────────────────────┤
  │ 그래프        │ Neo4j          │ 관계 중심 질의           │
  │ (Graph)      │                │ SNS, 추천, 지식 그래프    │
  └──────────────┴────────────────┴────────────────────────┘

  RDBMS vs NoSQL — 어떤 것을 선택할 것인가:
    데이터 구조가 명확하고 관계가 복잡 → RDBMS
    스키마가 자주 변하고 수평 확장이 필요 → NoSQL
    트랜잭션(ACID)이 핵심 → RDBMS
    가용성과 성능이 최우선 → NoSQL
    
    현실에서는 둘을 함께 사용하는 경우가 많다 (Polyglot Persistence).
```

## 10. 정리 — 데이터베이스를 관통하는 원리

```
[원리 1] 추상화와 독립성: 3단계 스키마로 물리/논리를 분리.
  → 저장 방식을 바꿔도 앱에 영향 없음.

[원리 2] 관계형 모델: 모든 데이터를 테이블(집합)로 표현.
  → 수학적으로 엄밀, SQL로 선언적 질의.

[원리 3] 정규화: "관련 있는 것끼리 묶고, 관련 없는 것은 분리."
  → 이상 현상 제거. 트레이드오프로 반정규화도 존재.

[원리 4] ACID: 트랜잭션의 정확성 보장.
  원자성(Undo) + 일관성(제약) + 격리성(잠금/MVCC) + 지속성(WAL).

[원리 5] 인덱싱: 검색 O(n) → O(log n)으로 가속. 대가: 쓰기 성능↓, 공간↑.
  → B+ 트리가 표준. 최좌선 접두사 원칙.

[원리 6] CAP 정리: 분산 시스템에서 C, A, P 중 최대 2개만 동시에 보장.
  → 현실적으로 P는 필수 → C vs A의 선택.

[원리 7] RDBMS vs NoSQL: 트레이드오프.
  RDBMS = 정확성(ACID) + 구조적 질의(SQL).
  NoSQL = 확장성 + 유연성 + 성능.

외워야 할 것:
  🔴 키의 종류 (슈퍼키, 후보키, 기본키, 외래키)와 관계
  🔴 정규형 (1NF~BCNF) 각각의 의미
  🔴 ACID 네 가지 속성과 구현 방법
  🔴 격리 수준 4단계와 각 수준에서 허용되는 이상 현상
  🔴 B+ 트리가 DB 인덱스 표준인 이유
  🔴 복합 인덱스의 최좌선 접두사 원칙
  🔴 CAP 정리
  🔴 NoSQL 4유형과 각각의 적합한 사례

유도할 수 있는 것:
  🟢 이상 현상이 왜 발생하는가 (중복 + 혼합 개념)
  🟢 정규화 과정 (FD 분석 → 분해)
  🟢 2PL이 직렬 가능성을 보장하는 이유
  🟢 MVCC에서 읽기가 블로킹되지 않는 이유
  🟢 CAP에서 C+A+P가 동시에 불가능한 이유
```
