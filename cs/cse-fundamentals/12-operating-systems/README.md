## 1. 출발점: 운영체제는 왜 존재하는가

### 1.1 OS가 없으면 어떻게 되는가

```
OS 없는 컴퓨터:
  - 프로그램 하나만 실행 가능 (다중 실행 불가)
  - 프로그래머가 하드웨어를 직접 제어해야 함 (디스크 섹터, 메모리 주소...)
  - 한 프로그램이 다른 프로그램의 메모리를 덮어쓸 수 있음 (보호 없음)
  - 여러 사용자가 동시에 사용할 수 없음

OS의 역할 — 두 가지로 요약:

  (1) 추상화 (Abstraction): 복잡한 하드웨어를 단순한 인터페이스로 감싼다.
      프로그래머는 "디스크의 섹터 137번에 512바이트를 쓴다"가 아니라
      "파일에 데이터를 쓴다"라고만 하면 된다.

  (2) 자원 관리 (Resource Management): CPU, 메모리, 디스크, 네트워크를
      여러 프로그램이 공유하도록 중재한다.
      → 공정하게, 효율적으로, 안전하게.
```

### 1.2 커널 모드와 유저 모드 — 왜 권한을 나누는가

```
🔴 [원리] 이중 모드 (Dual Mode):

  유저 모드: 일반 프로그램이 실행. 하드웨어 직접 접근 불가.
  커널 모드: OS 커널이 실행. 모든 하드웨어 접근 가능.

왜 나누는가:
  악의적이거나 버그가 있는 프로그램이 하드웨어를 직접 건드리면
  다른 프로그램이나 OS 자체를 망가뜨릴 수 있다.
  
  → 유저 프로그램은 "시스템 콜"을 통해서만 OS에 서비스를 요청할 수 있다.
  → 시스템 콜 = "유저 → 커널 모드 전환"의 관문

  프로그램: "파일을 읽고 싶어요" → 시스템 콜 read()
  OS: 권한 확인 → 디스크 접근 → 데이터 반환
  프로그램: 데이터를 받아 사용

  시스템 콜의 비용:
    모드 전환 = 수백~수천 사이클의 오버헤드
    → 시스템 콜을 최소화하는 것이 성능 최적화의 기본
```

## 2. 프로세스와 스레드 — "실행의 단위"

### 2.1 프로세스란 — 프로그램 ≠ 프로세스

```
🔴 [정의]
  프로그램: 디스크에 저장된 실행 파일 (정적)
  프로세스: 프로그램이 메모리에 올라와 실행 중인 상태 (동적)
  
  같은 프로그램을 두 번 실행하면 → 프로세스 2개 (독립적!)

프로세스의 메모리 구조:

  높은 주소 ┌──────────────┐
           │    스택       │  ← 함수 호출, 지역변수. 아래로 성장
           │      ↓       │
           │              │  ← 빈 공간
           │      ↑       │
           │     힙       │  ← 동적 할당(malloc/new). 위로 성장
           ├──────────────┤
           │   데이터      │  ← 전역변수, 정적변수
           ├──────────────┤
           │   코드(텍스트) │  ← 기계어 명령어 (읽기 전용)
  낮은 주소 └──────────────┘

  각 프로세스는 이 구조를 독립적으로 가진다.
  → 한 프로세스가 죽어도 다른 프로세스에 영향 없음 (격리!)
```

### 2.2 프로세스 상태 — 왜 이 상태들이 필요한가

```
🔴 [정의] 프로세스 상태 전이:

  New → Ready → Running → Terminated
                  ↕
                Waiting (Blocked)

  New:     생성됨. 아직 준비 안 됨.
  Ready:   실행 준비 완료. CPU를 기다리는 중.
  Running: CPU에서 실행 중. (한 코어에 하나만 가능)
  Waiting: I/O나 이벤트를 기다리는 중. CPU가 필요 없는 상태.
  Terminated: 실행 완료.

  Running → Waiting: I/O 요청 (디스크 읽기 등)
  Waiting → Ready:  I/O 완료 (데이터 도착)
  Running → Ready:  시간 할당량 소진 (선점 스케줄링)
  Ready → Running:  스케줄러가 이 프로세스를 선택

왜 Waiting 상태가 필요한가:
  프로세스가 I/O를 기다리는 동안 CPU를 놀리면 낭비.
  Waiting으로 보내고 다른 Ready 프로세스에게 CPU를 준다.
  → CPU 이용률 극대화!
```

### 2.3 문맥 교환 — 왜 이것이 비용인가

```
🔴 [정의] 문맥 교환 (Context Switch):
  실행 중인 프로세스 A를 멈추고, 프로세스 B를 실행하는 과정.

  Step 1: A의 상태(레지스터, PC, 스택 포인터 등)를 PCB에 저장
  Step 2: B의 상태를 PCB에서 복원
  Step 3: B를 실행

  PCB (Process Control Block):
    프로세스의 "이력서" — PID, 상태, 레지스터 값, 메모리 정보, 열린 파일 등

왜 이것이 비용인가:
  문맥 교환 동안 CPU는 "유용한 일"을 하지 않는다.
  레지스터 저장/복원, TLB 플러시, 캐시 미스 증가...
  → 보통 1~10 마이크로초. 초당 수천~수만 번이면 상당한 오버헤드.
  
  → 문맥 교환이 너무 잦으면: 오버헤드로 성능 저하
  → 문맥 교환이 너무 드물면: 반응 시간(응답성) 저하
  → 적절한 균형이 필요 → 스케줄링 알고리즘의 설계 목표
```

### 2.4 스레드 — 왜 프로세스만으로는 부족한가

```
🔴 [정의] 스레드 (Thread): 프로세스 내의 실행 흐름

  프로세스: 독립된 메모리 공간. 프로세스 간 통신이 비쌈.
  스레드: 같은 프로세스의 코드, 데이터, 힙을 공유. 스택만 별도.

  프로세스 A:                    프로세스 B:
  ┌────────────────┐            ┌────────────────┐
  │ 스택1 │ 스택2   │            │    스택         │
  │ (T1)  │ (T2)   │            │               │
  ├────────────────┤            ├────────────────┤
  │     힙 (공유)   │            │     힙         │
  ├────────────────┤            ├────────────────┤
  │   데이터 (공유)  │            │   데이터        │
  ├────────────────┤            ├────────────────┤
  │   코드 (공유)    │            │   코드          │
  └────────────────┘            └────────────────┘

왜 스레드를 쓰는가:
  (1) 생성/종료가 프로세스보다 훨씬 빠르다 (메모리 복제 불필요)
  (2) 스레드 간 통신이 빠르다 (같은 메모리 공유 → 복사 불필요)
  (3) 문맥 교환이 가볍다 (주소 공간 전환 불필요)

대가:
  (1) 하나의 스레드가 죽으면 프로세스 전체가 영향받을 수 있다
  (2) 공유 메모리 → 동기화 문제 발생! (§4에서 상세)

🔵 [CS 연결]
  웹 서버: 요청마다 스레드 생성 (또는 스레드 풀)
  브라우저: UI 스레드 + 렌더링 스레드 + 네트워크 스레드
  게임: 물리 스레드 + 렌더링 스레드 + AI 스레드
```

## 3. CPU 스케줄링 — "누구에게 CPU를 줄 것인가"

### 3.1 스케줄링이 왜 필요한가

```
CPU는 하나(또는 몇 개)인데, Ready 프로세스는 여러 개.
누구를 먼저 실행할 것인가? → 스케줄링 알고리즘이 결정.

🔴 성능 지표:
  CPU 이용률: CPU가 일하는 시간 비율 (높을수록 좋음)
  처리량(Throughput): 단위 시간당 완료 프로세스 수 (높을수록 좋음)
  반환 시간(Turnaround): 제출~완료까지 걸린 총 시간 (낮을수록 좋음)
  대기 시간(Waiting): Ready 큐에서 기다린 시간 (낮을수록 좋음)
  응답 시간(Response): 제출~첫 응답까지 시간 (낮을수록 좋음)

  이 지표들은 서로 충돌한다:
    처리량 최대화 ↔ 응답 시간 최소화 (트레이드오프!)
```

### 3.2 주요 스케줄링 알고리즘 — 각각의 존재 이유

```
🔴 FCFS (First Come First Served):
  먼저 온 순서대로 실행. 비선점.
  문제: 호위 효과(Convoy Effect) — 긴 작업이 먼저 오면 뒤의 짧은 작업들이 모두 기다림.
  → 단순하지만 비효율적.

🔴 SJF (Shortest Job First):
  실행 시간이 가장 짧은 것을 먼저. 비선점.
  🟢 평균 대기 시간이 최소임을 증명 가능.
  
  왜 최적인가:
    짧은 작업을 먼저 끝내면, 뒤에서 기다리는 작업의 수가 빨리 줄어든다.
    → 전체 대기 시간의 합이 최소.
  
  문제: 실행 시간을 미리 알 수 없다!
    → 과거 실행 시간으로 예측 (지수 이동 평균)
  문제: 기아(Starvation) — 긴 작업이 계속 밀려남
    → 에이징(Aging)으로 해결: 오래 기다린 작업의 우선순위를 높임

🔴 Round Robin (RR):
  각 프로세스에 시간 할당량(time quantum, q)을 주고 순환.
  q가 지나면 선점하여 Ready 큐 뒤로 보냄.
  
  왜 존재하는가: 공정성 + 응답 시간 보장
    모든 프로세스가 최대 (n-1)×q 시간 안에 CPU를 받음.
  
  q의 크기가 핵심:
    q가 너무 크면 → FCFS와 같아짐 (응답 시간 나쁨)
    q가 너무 작으면 → 문맥 교환이 너무 잦아 오버헤드 폭증
    보통 q = 10~100ms

🔴 MLFQ (Multi-Level Feedback Queue):
  여러 우선순위 큐. 높은 우선순위부터 RR로 실행.
  
  규칙:
    새 프로세스: 최고 우선순위 큐에 배치
    시간 할당량을 다 쓰면: 한 단계 낮은 큐로 이동 (CPU-bound로 판단)
    I/O로 일찍 반납하면: 높은 큐에 유지 (I/O-bound로 판단)
    주기적으로 모든 프로세스를 최고 큐로 올림 (기아 방지)
  
  왜 이것이 현실에서 쓰이는가:
    짧은 대화형 작업 → 높은 우선순위에서 빠르게 처리 (응답 시간 ↑)
    긴 배치 작업 → 낮은 우선순위에서 천천히 처리 (처리량 유지)
    → SJF의 "실행 시간 예측 불필요" 버전!
    
    실행해보면서 자동으로 CPU-bound/I/O-bound를 분류하는 것이 핵심.

🔵 [CS 연결]
  Linux CFS (Completely Fair Scheduler):
    "완전히 공정한 스케줄러" — 각 프로세스에 가상 실행 시간을 추적,
    가장 적게 실행된 프로세스를 우선 실행.
    레드-블랙 트리(Ch.09)로 구현 → O(log n) 선택.
```

## 4. 동기화 — "함께 쓰면 생기는 문제"

### 4.1 경쟁 상태 — 왜 공유 메모리가 위험한가

```
🔴 [정의] 경쟁 상태 (Race Condition):
  여러 스레드가 공유 데이터에 동시에 접근하고, 실행 순서에 따라 결과가 달라지는 상황.

예시: 은행 계좌 (잔고 = 1000)

  스레드 A: 잔고 += 500          스레드 B: 잔고 -= 200
  
  기대 결과: 1000 + 500 - 200 = 1300

  실제로 일어날 수 있는 일:
    A: 잔고 읽기 (1000)
    B: 잔고 읽기 (1000)        ← A의 결과가 아직 안 써짐!
    A: 잔고 쓰기 (1500)
    B: 잔고 쓰기 (800)         ← A의 결과를 덮어씀!
    
    최종: 800 (500원 증발!)

왜 이런 일이 생기는가:
  "읽기-수정-쓰기"가 원자적(atomic)이지 않기 때문.
  중간에 다른 스레드가 끼어들 수 있다.
  → 해결: 이 과정을 "아무도 방해 못 하는 구간"으로 만든다 → 임계 구역
```

### 4.2 임계 구역과 상호 배제

```
🔴 [정의] 임계 구역 (Critical Section):
  공유 자원에 접근하는 코드 영역. 한 번에 하나의 스레드만 실행해야 한다.

  임계 구역 문제의 세 조건:
    (1) 상호 배제 (Mutual Exclusion): 한 번에 하나만 진입
    (2) 진행 (Progress): 아무도 안 쓰고 있으면 들어갈 수 있어야
    (3) 한정 대기 (Bounded Waiting): 무한히 기다리지 않아야
```

### 4.3 동기화 도구 — 왜 여러 가지가 필요한가

```
🔴 뮤텍스 (Mutex):
  "잠금"과 "해제" 두 연산. 잠근 스레드만 해제할 수 있다.
  
  lock(mutex)        ← 다른 스레드가 잠갔으면 기다림
  // 임계 구역
  unlock(mutex)      ← 다른 스레드가 진입 가능
  
  비유: 화장실 문 잠금. 열쇠를 가진 사람만 사용 가능.

🔴 세마포어 (Semaphore):
  정수 값을 가진 동기화 변수. 두 연산: wait(P)와 signal(V).
  
  wait(S):   S > 0이면 S -= 1하고 진행, S == 0이면 기다림
  signal(S): S += 1하고 기다리는 스레드가 있으면 깨움
  
  이진 세마포어 (S = 0 or 1): 뮤텍스와 유사
  카운팅 세마포어 (S = n): n개의 자원을 동시에 허용
  
  비유: 주차장. 남은 자리 수 = S. 차가 들어가면 S--, 나오면 S++.
  S = 0이면 기다려야 한다.

  왜 뮤텍스와 세마포어 둘 다 필요한가:
    뮤텍스: 소유권이 있다 (잠근 사람만 풀 수 있다) → 임계 구역 보호
    세마포어: 소유권이 없다 → 생산자-소비자 같은 신호(signaling) 패턴에 적합

🔴 모니터 (Monitor):
  "뮤텍스 + 조건 변수"를 하나로 묶은 고수준 동기화.
  한 번에 하나의 스레드만 모니터 안에 있을 수 있다.
  
  조건 변수 (Condition Variable):
    wait(cond): "조건이 충족될 때까지 기다린다" (잠금 해제 + 대기)
    signal(cond): "기다리는 스레드를 하나 깨운다"
  
  왜 모니터가 필요한가:
    뮤텍스/세마포어는 저수준이어서 실수하기 쉽다.
    잠금을 걸고 풀지 않으면 데드락. 잠금 순서를 잘못하면 데드락.
    모니터는 이런 실수를 구조적으로 방지한다.
    
  🔵 Java의 synchronized 블록 = 모니터
     Python의 threading.Condition = 조건 변수
```

### 4.4 고전적 동기화 문제 — 왜 이것들이 유명한가

```
이 문제들은 실제 시스템에서 반복적으로 나타나는 패턴의 원형이다.

🔵 생산자-소비자 (Producer-Consumer):
  생산자가 데이터를 버퍼에 넣고, 소비자가 꺼내 쓴다.
  버퍼가 가득 차면 생산자가 기다림. 비면 소비자가 기다림.
  → 세마포어 2개 (full, empty) + 뮤텍스로 해결
  → 메시지 큐, 파이프라인, 로그 시스템의 기반 패턴

🔵 독자-저자 (Readers-Writers):
  여러 독자는 동시에 읽어도 됨. 저자가 쓸 때는 아무도 접근 불가.
  → DB의 동시성 제어, 캐시 업데이트의 기반 패턴

🔵 식사하는 철학자 (Dining Philosophers):
  5명의 철학자가 원탁에 앉아 포크 5개를 공유. 양쪽 포크가 있어야 식사.
  모두 왼쪽 포크를 집으면 → 데드락!
  → 자원 경쟁과 데드락의 본질을 보여주는 문제
```

## 5. 교착 상태 (Deadlock) — 모두가 멈추는 순간

### 5.1 데드락이란

```
🔴 [정의] 데드락:
  프로세스들이 서로가 가진 자원을 기다리며 무한히 대기하는 상태.

  프로세스 A: 자원 1을 가지고, 자원 2를 기다림
  프로세스 B: 자원 2를 가지고, 자원 1을 기다림
  → 둘 다 영원히 기다림!

  일상 비유: 좁은 다리에서 양쪽에서 온 차가 마주보고 있으면
  둘 다 물러나지 않으면 영원히 못 지나감.
```

### 5.2 데드락의 4가지 필요 조건 — 왜 "4가지 모두"인가

```
🔴 [정의] 데드락이 발생하려면 다음 네 조건이 동시에 성립해야 한다:

  (1) 상호 배제 (Mutual Exclusion):
      자원을 한 번에 하나의 프로세스만 사용 가능
  
  (2) 점유와 대기 (Hold and Wait):
      자원을 가진 채로 추가 자원을 기다림
  
  (3) 비선점 (No Preemption):
      다른 프로세스의 자원을 강제로 빼앗을 수 없음
  
  (4) 순환 대기 (Circular Wait):
      P₁→P₂→P₃→...→P₁ 형태의 순환 대기 체인

  하나라도 깨지면 데드락이 발생하지 않는다.
  → 이것이 데드락 예방/회피/탐지 전략의 기반.
```

### 5.3 데드락 처리 전략

```
🔴 (1) 예방 (Prevention): 4 조건 중 하나를 원천 차단
  순환 대기 깨기: 모든 자원에 번호를 매기고, 번호 순서대로만 요청하도록 강제
  점유와 대기 깨기: 필요한 모든 자원을 한 번에 요청
  → 실용적이지만 자원 이용률이 떨어질 수 있음

🔴 (2) 회피 (Avoidance): 데드락이 일어날 "가능성"이 있으면 자원을 주지 않음
  은행원 알고리즘 (Banker's Algorithm):
    "이 자원을 주면 안전한 상태를 유지할 수 있는가?"
    안전 상태: 모든 프로세스가 순서대로 완료 가능한 상태
    
    왜 "은행원"인가: 은행이 대출할 때 파산하지 않을 만큼만 빌려주는 것과 같음.

🔴 (3) 탐지 + 복구 (Detection + Recovery):
  데드락을 허용하되, 발생하면 감지하고 해결
  탐지: 자원 할당 그래프에서 사이클 탐색 (DFS)
  복구: 프로세스 종료 또는 자원 강제 회수

🔴 (4) 무시 (Ostrich Algorithm):
  "데드락은 드물고, 처리 비용이 크니까 무시하자"
  → 대부분의 범용 OS(Linux, Windows)가 실제로 채택하는 전략!
  → 데드락 발생 시 사용자가 프로세스를 수동으로 종료
  
  왜 이것이 합리적인가:
    데드락 예방/회피의 오버헤드 > 가끔 발생하는 데드락의 비용
    → 실용적 판단
```

## 6. 메모리 관리 — "한정된 공간을 나눠 쓰기"

### 6.1 왜 메모리 관리가 필요한가

```
여러 프로세스가 메모리를 함께 사용해야 한다.
  - 한 프로세스가 다른 프로세스의 메모리를 읽으면 안 된다 (보호)
  - 각 프로세스는 자신만의 주소 공간이 있다고 느껴야 한다 (추상화)
  - 물리 메모리보다 큰 프로그램도 실행할 수 있어야 한다 (가상화)
```

### 6.2 페이징 — 왜 이것이 표준인가

```
🔴 [정의] 페이징 (Paging):
  가상 주소 공간을 고정 크기 블록(페이지, 보통 4KB)으로 나누고,
  물리 메모리도 같은 크기 블록(프레임)으로 나누어,
  페이지를 프레임에 매핑한다.

  가상 주소 → 페이지 테이블 → 물리 주소

  가상 주소 공간:          물리 메모리:
  ┌──────┐ 페이지 0       ┌──────┐ 프레임 0
  │ 코드  │ ──────────→   │ (다른) │
  ├──────┤ 페이지 1       ├──────┤ 프레임 1
  │ 데이터 │ ──────→      │ 코드  │ ← 페이지 0
  ├──────┤              ├──────┤ 프레임 2
  │  힙  │ ──────→      │  힙  │ ← 페이지 2
  ├──────┤              ├──────┤ 프레임 3
  │ 스택  │ ──────→      │데이터 │ ← 페이지 1
  └──────┘              ├──────┤ 프레임 4
                        │ 스택  │ ← 페이지 3
                        └──────┘

왜 페이징인가 — 연속 할당의 문제:
  연속 할당: 프로세스를 연속된 메모리 블록에 배치
  문제: 외부 단편화 — 빈 공간이 있어도 조각나서 사용 불가
  
  ┌──┐ ┌──────┐ ┌──┐ ┌──────┐ ┌──┐
  │P1│ │ 빈   │ │P2│ │ 빈   │ │P3│
  └──┘ └──────┘ └──┘ └──────┘ └──┘
  
  빈 공간 합계 = 충분, 하지만 연속된 큰 블록이 없어서 할당 불가!

  페이징: 고정 크기 → 어떤 빈 프레임이든 사용 가능 → 외부 단편화 없음!
  
  대가: 내부 단편화 — 마지막 페이지가 꽉 차지 않으면 공간 낭비
  (최대 4KB - 1 = 한 페이지 미만의 낭비. 외부 단편화보다 훨씬 경미)
```

### 6.3 페이지 테이블과 TLB — 왜 캐시가 필요한가

```
페이지 테이블: 가상 페이지 번호 → 물리 프레임 번호의 매핑

  가상 주소 = [페이지 번호 | 오프셋]
  물리 주소 = [프레임 번호 | 오프셋]  (오프셋은 동일)

문제: 페이지 테이블도 메모리에 있다.
  메모리 접근 1번을 위해 → 페이지 테이블 접근(1번) + 실제 접근(1번) = 2번!
  → 속도가 절반으로!

해결: TLB (Translation Lookaside Buffer)
  최근 사용된 페이지 변환을 캐시하는 작은 고속 메모리.
  
  TLB 히트: 1 사이클로 변환 (99%+의 접근)
  TLB 미스: 페이지 테이블 접근 필요 (느림)
  
  왜 TLB가 작동하는가: 지역성! (Ch.11)
    프로그램은 소수의 페이지를 반복 접근하므로,
    작은 TLB(~64-1024 엔트리)로도 대부분의 접근을 커버.
```

## 7. 가상 메모리 — "없는 메모리를 있는 것처럼"

### 7.1 가상 메모리란 — 왜 이것이 필요한가

```
🔴 [핵심 아이디어]
  물리 메모리(RAM)보다 큰 프로그램도 실행할 수 있다!
  사용하지 않는 페이지는 디스크(swap)에 저장하고,
  필요할 때만 메모리로 가져온다.

  각 프로세스는 자신만의 거대한 가상 주소 공간(예: 2⁶⁴ 바이트)을 가진다.
  실제로는 물리 메모리의 일부만 사용하고, 나머지는 디스크에 있다.

왜 가능한가:
  프로그램은 한 번에 전체 메모리를 쓰지 않는다 (지역성!).
  지금 쓰는 부분만 메모리에, 안 쓰는 부분은 디스크에 → 효율적.
```

### 7.2 요구 페이징과 페이지 폴트

```
🔴 [정의] 요구 페이징 (Demand Paging):
  페이지를 미리 올리지 않고, 접근할 때 올린다.

  접근 → 페이지 테이블 확인 → 
    메모리에 있음 (valid) → 정상 접근
    메모리에 없음 (invalid) → 페이지 폴트!

  페이지 폴트 처리:
    1. OS가 트랩을 받음
    2. 디스크에서 해당 페이지를 찾음
    3. 빈 프레임에 적재 (없으면 기존 페이지를 교체)
    4. 페이지 테이블 업데이트
    5. 중단된 명령어를 재실행

  페이지 폴트 비용:
    메모리 접근: ~100ns
    디스크 접근: ~10ms = 100,000배 느림!
    
    페이지 폴트율이 0.1%만 되어도 성능이 100배 느려짐.
    → 페이지 교체 알고리즘이 매우 중요한 이유!
```

### 7.3 페이지 교체 알고리즘 — 무엇을 버릴 것인가

```
🔴 메모리가 가득 찼는데 새 페이지가 필요하면, 기존 페이지를 하나 버려야 한다.
  어떤 것을 버릴 것인가?

  OPT (Optimal): 앞으로 가장 오래 사용되지 않을 페이지를 교체.
    → 이론적 최적. 하지만 미래를 알 수 없으므로 실현 불가능!
    → 다른 알고리즘의 성능 기준선(벤치마크)으로 사용.

  FIFO: 가장 먼저 올라온 페이지를 교체.
    → 단순하지만 성능이 나쁠 수 있음.
    → 벨라디의 모순: 프레임 수를 늘렸는데 폴트가 증가하는 현상!
       (FIFO에서만 발생. 직관에 반하지만 실제로 일어남.)

  LRU (Least Recently Used): 가장 오래 사용되지 않은 페이지를 교체.
    왜 좋은가: 시간적 지역성 — 최근에 안 쓴 것은 앞으로도 안 쓸 가능성 높다.
    → OPT에 가까운 성능.
    문제: 완벽한 구현이 비쌈 (매 접근의 시간을 기록해야).
    
  Clock (Second Chance): LRU의 실용적 근사.
    참조 비트(reference bit) 사용.
    시계 바늘처럼 순회하며:
      참조 비트 1 → 0으로 초기화하고 넘어감 (한 번 더 기회)
      참조 비트 0 → 교체!
    → 대부분의 OS가 실제로 사용하는 알고리즘.
```

### 7.4 스래싱 — 가상 메모리의 최악 상황

```
🔴 [정의] 스래싱 (Thrashing):
  페이지 폴트가 너무 빈번하여 CPU가 실제 작업보다 페이지 교체에 더 많은 시간을 쓰는 상태.

원인:
  동시에 실행되는 프로세스가 너무 많아서,
  각 프로세스의 워킹 셋(자주 쓰는 페이지 집합)을 메모리에 유지할 수 없을 때.
  
  프로세스 A의 페이지를 밀어내고 B를 올림 → B가 A의 페이지 필요 → A를 다시 올림
  → 디스크 I/O만 반복, CPU 이용률 급락!

해결:
  워킹 셋 모델: 각 프로세스의 워킹 셋 크기를 추적.
  워킹 셋 합계 > 물리 메모리이면 → 프로세스 일부를 중단(suspend).
  → 적은 수의 프로세스라도 제대로 실행하는 것이 모두 스래싱보다 낫다.
```

## 8. 파일 시스템 — "데이터를 영구히 저장하기"

### 8.1 파일 시스템이란 — 왜 필요한가

```
디스크는 번호 붙은 블록(섹터)의 나열일 뿐이다.
  "섹터 12345에 512바이트를 쓴다" → 너무 저수준!

파일 시스템의 역할:
  블록들을 "파일"과 "디렉터리"라는 추상화로 감싼다.
  → "report.txt에 데이터를 쓴다" → OS가 적절한 블록을 찾아 저장
```

### 8.2 파일 할당 방식 — 데이터를 디스크 어디에 놓는가

```
🔴 (1) 연속 할당: 파일을 연속된 블록에 저장.
  장점: 순차 읽기/임의 접근 빠름.
  단점: 외부 단편화, 파일 크기 변경 어려움.

🔴 (2) 연결 할당: 각 블록이 다음 블록의 포인터를 가짐 (연결 리스트).
  장점: 단편화 없음, 파일 크기 유연.
  단점: 임의 접근 느림 (처음부터 따라가야), 포인터 공간 오버헤드.
  → FAT (File Allocation Table): 포인터를 별도 테이블에 모아둠.

🔴 (3) 인덱스 할당 (i-node): 인덱스 블록이 데이터 블록 주소를 저장.
  장점: 임의 접근 빠름. 단편화 없음.
  → Unix/Linux의 표준 방식.
  
  i-node 구조:
    직접 포인터: 12개 → 작은 파일은 이것만으로 충분
    간접 포인터: 1단 간접 → 포인터 블록 → 데이터 블록
    이중 간접: 포인터 → 포인터 → 데이터
    삼중 간접: 포인터 → 포인터 → 포인터 → 데이터
    
    왜 이런 계층:
      대부분의 파일은 작다 (직접 포인터로 충분)
      큰 파일도 지원해야 한다 (간접 포인터로 확장)
      → 작은 파일은 빠르게, 큰 파일도 가능하게 — 실용적 균형
```

### 8.3 저널링 — 왜 필요한가

```
🔴 [문제] 파일 쓰기 도중 전원이 꺼지면?
  메타데이터(i-node)와 데이터가 불일치할 수 있다.
  → 파일 시스템 손상!

🔴 [해결] 저널링 (Journaling):
  변경 사항을 먼저 "로그(저널)"에 기록한 후, 실제 적용.
  전원이 꺼져도 로그를 보고 복구 가능.
  
  → ext4, NTFS, APFS 모두 저널링 사용.
  → 데이터베이스의 WAL (Write-Ahead Log)과 같은 원리! (Ch.15)
```

## 10. 정리 — 운영체제를 관통하는 원리

```
[원리 1] 추상화: 복잡한 하드웨어를 단순한 인터페이스로 감싼다.
  파일 = 디스크 블록의 추상화. 프로세스 = CPU 실행의 추상화. 가상 메모리 = RAM의 추상화.

[원리 2] 가상화: 각 프로세스에게 "나만의 컴퓨터"라는 환상을 준다.
  각 프로세스는 자신만의 CPU(스케줄링), 메모리(가상 메모리), 파일을 가진다고 느낀다.

[원리 3] 공유와 보호의 균형: 자원을 효율적으로 공유하되, 서로를 보호한다.
  커널/유저 모드 분리, 가상 주소 공간 격리, 파일 접근 권한.

[원리 4] 공간-시간 트레이드오프 (다시):
  캐시, TLB = 공간을 써서 시간을 번다.
  스왑 = 시간을 써서 공간을 번다.

[원리 5] 지역성이 모든 것을 가능하게 한다.
  캐시, TLB, 요구 페이징, 워킹 셋 — 모두 지역성에 의존.

[원리 6] 동시성은 정확성을 위협한다.
  공유 자원 + 동시 접근 = 경쟁 상태.
  → 동기화 도구(뮤텍스, 세마포어, 모니터)로 해결.
  → 과도한 동기화 = 성능 저하 및 데드락 위험.

[원리 7] 데드락의 4 조건: 하나만 깨면 된다.
  현실에서는 무시 전략(오스트리치)이 가장 흔하다.

외워야 할 것:
  🔴 프로세스 상태 전이 다이어그램 (New → Ready → Running → Waiting → Terminated)
  🔴 프로세스 vs 스레드의 차이 (메모리 공유 여부)
  🔴 스케줄링 알고리즘별 특성 (FCFS, SJF, RR, MLFQ)
  🔴 데드락의 4 조건과 처리 전략 4가지
  🔴 페이징: 가상 주소 → 페이지 번호 + 오프셋
  🔴 페이지 교체 알고리즘: OPT, FIFO, LRU, Clock
  🔴 스래싱의 정의와 원인
  🔴 i-node 구조 (직접 + 간접 포인터)

유도할 수 있는 것:
  🟢 SJF가 평균 대기시간 최소인 이유 (교환 논법)
  🟢 페이징이 외부 단편화를 없애는 이유 (고정 크기)
  🟢 TLB가 작동하는 이유 (지역성 → 소수 페이지 반복 접근)
  🟢 LRU가 OPT에 가까운 이유 (시간적 지역성)
  🟢 스래싱 발생 조건 (워킹 셋 합 > 물리 메모리)
```
