# 다층 웹 보안 방어 (Defense in Depth) — 인프라 관점

> "단일 방어가 아닌 N 레이어가 동시에 작동" 패턴.
> 한 레이어 뚫려도 다음 레이어가 막는 구조 설계.

---

## 1. 다층 방어의 본질

```
공격자 → [Layer 1] → [Layer 2] → ... → [Layer N] → 자원
            │            │
            └─ 뚫림      └─ 막힘
```

각 레이어는:
- 다른 종류의 공격 시그널을 봄.
- 다른 시간 척도에서 작동 (즉시 / 분 / 시간).
- 다른 비용/노이즈 트레이드오프.
- 독립적으로 진화 가능.

---

## 2. 외부 검색 사이트 의 9 레이어 분석 — 모범 사례

| # | 레이어 | 위치 | 핵심 기술 | 차단 대상 |
|---|--------|------|----------|----------|
| 1 | 요청 암호화 | 프론트 → 전송 | dynapath: AES + 시간 키 + 핑거프린트 | curl, Postman, 직접 호출 |
| 2 | JS 난독화 | 프론트 | RC4 문자열 + 제어 흐름 평탄화 | 코드 역공학 |
| 3 | 디바이스 핑거프린팅 | 프론트 | Canvas, WebGL, 화면 정보 | Headless 브라우저 |
| 4 | 안티 디버깅 | 프론트 | debugger 문, 콘솔 감지 | DevTools 분석 |
| 5 | 세션 관리 | 백엔드 | 경로별 분리, 빠른 만료 | 쿠키 복사 |
| 6 | 행동 분석 | 백엔드 | 마우스/키 입력 패턴 | 단순 자동화 |
| 7 | 이벤트 신뢰도 | 프론트 | event.isTrusted | JS 발생 이벤트 |
| 8 | 응답 구조 분리 | 백엔드 | 핵심 데이터를 암호화 API 분리 | 공개 API 만 사용한 크롤러 |
| 9 | TLS / Rate limiting | 네트워크 | 표준 보안 + 호출 빈도 제한 | 폭력 공격 |

핵심 통찰: **각 레이어가 다른 도구·다른 위치·다른 시그널**.

## 3. 레이어 설계 원칙

### 3.1 다양성 — 같은 종류의 방어 N개는 의미 없음
- "방화벽 + 방화벽 + 방화벽" 은 1 레이어.
- "방화벽 + WAF + Rate limit + 행동 분석" 은 4 레이어.

### 3.2 독립성 — 한 레이어 우회가 다른 레이어 우회를 의미하지 않게
- 인증 토큰 탈취해도 행동 패턴이 다르면 차단.
- 핑거프린트 위조해도 암호화 키가 안 맞으면 거부.

### 3.3 비대칭 — 공격자 비용 vs 방어자 비용
- 좋은 방어: 공격자에게 비싸고 방어자에게 싸야.
- Canvas 핑거프린트: 위조에 GPU 자원 필요 (공격 비용 ↑↑) vs 1줄 JavaScript (방어 비용 ↓).
- 나쁜 방어: 정교한 captcha 가 정상 사용자도 짜증나게 (방어 비용도 큼).

### 3.4 대각선 방어 — 한 차원만 막지 않게
- 시그널 차원: 인증 + 권한 + 봇 탐지 + 데이터 검증.
- 시간 차원: 즉시 (Rate limit) + 분 (행동 패턴) + 시간 (계정 분석).
- 위치 차원: 프론트 + 네트워크 + 백엔드 + DB.

## 4. 응답 구조 분리 — 데이터 가치 차별화

외부 검색 사이트 의 핵심 설계:
```json
// 검색 API (공개, 단순 인증)
{
  "GD": "화장품|향수|메이크업 화장품|...",
  "SC": "G1201|G1301|S120907|S128302"
}
// → 어떤 상품이 어떤 코드인지 매핑 불가능

// 상세 API (dynaPath 암호화 필수)
{
  "tb_KT15List": [
    ["03", null, "화장품", null, "G1201,S120907,S128302"],
    ["03", null, "샴푸", null, "G1201,G1301"]
  ]
}
// → 상품별 코드 1:1 매핑 제공
```

### 통찰
- 공개 API 만 긁어가는 크롤러는 **불완전 데이터** 만 가져감.
- 가치 있는 매핑 정보는 강한 인증 API 만 제공.
- 즉 공격자가 가져갈 수 있는 데이터의 가치 자체를 차별화.

→ "차단" 대신 "가치 격하" 도 방어의 한 형태.

## 5. 행동 분석 — 봇과 사람의 통계적 차이

수집 시그널:
```
qt: 키보드 이벤트 패턴
fx: 마우스 좌표 이력
t:  키 입력 타이밍 배열
vn: 키 다운~업 간격
ca: Ctrl+V (붙여넣기) 감지
m:  한글/유니코드 입력
mx: 마우스 이벤트 존재
hf: 페이지 포커스 변경 시간
```

### 통계적 봇 판별
```
점수 = 0
if 마우스 이동 없이 클릭만:           +10
if 키 입력 간격이 완전히 일정:          +10
if 페이지 로드 후 즉시 클릭:           +10
if Ctrl+V 로 검색어 입력:              +5
if Canvas 핑거프린트 블랙리스트:        +50
if navigator.webdriver === true:       +100
if 점수 > 임계값: 차단
```

### 가치
- 단일 시그널로는 false positive 많음.
- 종합 점수가 임계 초과 → 강한 신호.
- 정상 사용자도 가끔 잘못 잡힐 수 있음 → 임계 조정 + 단계적 응답 (경고 → 차단).

## 6. 외부 API 보호 — 여러 모범 패턴

### 6.1 Rate Limiting
- IP 별 분당 N 요청.
- 토큰 별 시간당 N 요청.
- token bucket / leaky bucket 알고리즘.

```python
# Redis 기반 sliding window
async def check_rate_limit(ip, limit=60, window=60):
    key = f"rl:{ip}:{int(time.time() // window)}"
    count = await redis.incr(key)
    if count == 1:
        await redis.expire(key, window)
    return count <= limit
```

### 6.2 IP 블랙리스트 + TTL
```python
# 위반 시 자동 등록
await redis.set(f"bl:{ip}", "1", ex=3600)  # 1시간 차단

# 매 요청 시 확인
if await redis.exists(f"bl:{ip}"):
    return 403
```

### 6.3 단계적 차단 (Escalation)
- 첫 위반: 경고.
- 2번째: 1분 차단.
- 3번째: 1시간.
- 5번째 이상: 영구 차단 + 운영자 알림.

```python
violation_count = await redis.incr(f"vc:{ip}")
ttl_map = {1: 60, 2: 600, 3: 3600, 4: 86400}
ttl = ttl_map.get(violation_count, 86400 * 30)  # 영구 = 30일
await redis.set(f"bl:{ip}", "1", ex=ttl)
```

### 6.4 의심 패턴 자동 감지
- 단일 IP 가 10개 이상 다른 user-agent.
- 매 요청의 응답 크기가 거의 일정 (자동 파싱 신호).
- 정상 사용자가 거의 안 가는 deep page 만 접근.

→ 이상치 → 별도 큐로 격리 → 분석 후 차단 결정.

## 7. WAF (Web Application Firewall) 의 위치

다층 방어에서 WAF 의 역할:
- L1 정도 (네트워크 가까운 곳).
- 알려진 공격 패턴 차단 (SQL injection, XSS payload).
- ModSecurity 같은 룰셋 사용.

한계:
- 알려진 패턴만 → 0-day 못 막음.
- 우회 가능 (인코딩, 부분 분할).
- → WAF 만으로는 부족. 다른 레이어 병행.

## 8. 정당한 자동화 vs 적대적 크롤링 구분

### 정당한 자동화
- 자기 계정 데이터 백업.
- API 키로 인증된 접근.
- robots.txt 준수.
- Rate limit 안에서.

→ 인증 토큰 + Rate limit 만으로 충분.

### 적대적 크롤링
- 비인증 대량 접근.
- 다른 사용자의 데이터 수집.
- ToS 위반.

→ 9 레이어 + 행동 분석.

### 구분 어려운 경우
- 검색엔진 크롤러 (Googlebot 등) → 정당하지만 인증 없음.
- 화이트리스트 (User-Agent + IP 검증) 으로 통과.

---

## 9. 모니터링과 알람

방어 자체로 끝이 아님 — 결과 관찰 필수.

### 9.1 메트릭
- 레이어별 차단 수.
- IP/계정별 위반 횟수.
- false positive 의심 사례 (정상 사용자 신고).

### 9.2 알람
- 갑작스런 차단 폭증 → 공격 또는 정상 사용자 영향 의심.
- 특정 IP/계정의 반복 차단 → 인지된 공격자.
- 차단 0 → 방어 자체가 안 도는 신호.

---

## 10. 응용 포인트

- 단일 방어 대신 N 레이어 (다양성 + 독립성 + 대각선).
- 데이터 가치 차별화 — 공개 API 는 일부, 핵심은 인증 API.
- 행동 분석은 통계적 판별 — 종합 점수 + 단계적 응답.
- Rate limit + 단계적 블랙리스트 + 단계적 escalation.
- WAF 는 1 레이어, 다른 방어 병행.
- 정당한 자동화는 인증 + Rate limit 으로 통과 보장.
- 차단 자체가 아닌 차단 결과의 모니터링/알람도 시스템.
